# 成果物アーキテクチャ(要望要件)

**このドキュメントは要件であって設計ではない。** 「何を満たすべきか」「何を壊してはいけないか」「まだ決まっていないこと」を確定させるための文書で、テーブル定義や画面実装はここでは決めない。設計に進む前にこの内容へ合意を取る。

最終更新: 2026-08-04

## 1. なぜ今これを書くか

イベント動画テンプレートを追加したとき([README「動画は一等アセット」](../README.md#動画は一等アセットテンプレート制))、動画のためだけに作ったつもりの構造が、実は**すべての成果物に共通する形**だったことが分かった。

- 左に一覧、右に中身
- 一覧には複数の「テイク」が並ぶ
- 新規作成すると**型(テンプレート)を選ばされる**
- 各テイクは**素材 → 成果**のパイプラインを持ち、素材を足すとリッチになる

LPも同じ形になるべきで、ロゴのプレゼンテーションも、ガイドラインも同じ。つまり動画で作った構造は特殊解ではなく一般解だった。この気づきを一度きちんと言語化しないまま各成果物へ横展開すると、成果物ごとに似て非なる実装が3つ4つできて、後から統合できなくなる。

## 2. 見えてきた不変構造

```text
Brand
└── AssetType（ロゴプレゼン / LP / 動画 / バナー / ガイドライン …）
      ├── 既定テイク（型が1つに決まっているもの。未生成でも席がある）
      └── テイク（複数）
            ├── Template（作成時に選ぶ。以後不変）
            ├── Pipeline（素材 → 構造化 → 成果。段は型ごとに異なる）
            ├── Composition（テイク内部の構成。placementに何を入れるか）
            └── 公開状態（未公開が既定。どれが正典かは型ごとに決める）

Brand
└── MaterialLibrary（素材と構造化データ。テイクを横断して共有される）
```

**AssetTypeとTemplateを混同しない。** AssetTypeは「何を作るか」(動画・LP)、Templateは「どの型で作るか」(製品CM・イベントPV)。UIで型を選ばせるのはTemplateである。

**TemplateとCompositionを混同しない。** Templateはテイクの骨格で不変。Compositionはテイク内部の可変な中身で、既存の presentation asset catalog(`presentation_asset_definitions` + `logo_presentations.layout` の placement 機構)がまさにこれ。**placementはテイクではない**——これを混ぜると「1ロゴに複数プレゼン」と「1プレゼンの中に複数asset」が区別できなくなる。

## 3. 用語

| 用語 | 意味 | 現状の実装 |
|---|---|---|
| **AssetType** | 成果物の種類 | `brand_assets.asset_kind` |
| **Take**(テイク) | AssetTypeの1インスタンス。それ自体が納品物 | `brand_assets` の1行 |
| **Template** | テイクの型。作成時に確定し不変 | 動画のみ `metadata.template`。他は未導入 |
| **Pipeline** | 素材→成果の工程。段は型ごとに違う | 動画=Remotion、LP=LLM、プレゼン=クライアント解析 |
| **Run** | パイプラインの1回の実行。入力・コスト・エラーを持つ | `brand_generation_runs` |
| **Material** | テイクを横断して使える素材と構造化データ | **存在しない**(散在) |
| **Composition** | テイク内部の構成(placement割当) | `logo_presentations.layout` |

## 4. 要件

### R1. AssetTypeは共通の器を持つ

- R1.1 すべてのAssetTypeは、1ブランドに対して**0件以上のテイク**を持てる
- R1.2 テイクは `brand_assets` の行として表現する。AssetTypeごとに専用テーブルを作らない
- R1.3 テイクは必ず1つのTemplateに属する。**Templateは作成時に確定し、以後変更できない**(シーン構成・素材スロット・構造化プロンプトが変わるため)
- R1.4 Templateの一覧はコード側のレジストリを正本とし、DBに複製しない(現行 `lib/video/templates.ts` の方式を全AssetTypeへ一般化する)
- R1.5 テイクは公開状態を持ち、**既定は未公開**

### R2. 既定テイクの扱いを一般化する

動画では「製品紹介動画は全ブランドに提供するが、未生成のプレースホルダー行は作らない」とした。これを規則にする。

- R2.1 AssetTypeは「既定Template」を宣言できる
- R2.2 既定テイクは**行を持たずに一覧の1件目として合成表示**してよい。実体化は成果物が発生してから
- R2.3 既定テイクを使わない利用者に、公開もパブリッシュも強制しない

> **要検討**: 合成表示はAssetTypeが増えるほど分岐が増える。「初回オープン時に実体化する」方式との比較が必要(§10)。

### R3. パイプラインの段は型ごとに宣言する

slide-factoryの5段(入力→抽出→構造化→スタイリング→出力)をすべてに強制しない。実際に段が違う:

| Template | 実際の工程 | LLM |
|---|---|---|
| イベントPV | 素材整形(決定論) → ブリーフ → Remotion | 使わない |
| 製品CM | ソース → Brand Kit(LLM) → TTS → Remotion | 使う |
| ロゴプレゼン | SVG解析(クライアント・決定論) → placement割当 | 使わない |

- R3.1 Templateは**自分の段を宣言する**。共通の器は「段の並び」と「各段の状態」だけを知る
- R3.2 決定論でできる段にLLMを使わない。抽出は機械的、LLMは構造化だけ(slide-factoryの原則を継承)
- R3.3 各段は独立して再実行でき、**再実行は前の成果を壊さない**
- R3.4 実行の入力・コスト・エラーは `brand_generation_runs` に記録し、テイク単位で追える

### R4. 素材はテイクを横断して共有される(最重要かつ最大の新規実装)

これが今回の気づきの本体。素材と構造化データは特定のテイクの持ち物ではなく、**Brandの資産**である。

- R4.1 Brandは素材ライブラリを持つ。同じ写真・ロゴ・構造化データを動画とLPとバナーが**参照**する(コピーしない)
- R4.2 素材は出自(provenance)を持つ。手動アップロード / URL取得 / AI生成 / 派生物を区別する
- R4.3 **加工物は派生として記録する**。暗背景用にノックアウトしたロゴは、原本とは別の派生素材であり、原本への参照と加工の種類を持つ
- R4.4 構造化データ(EventBrief / Brand Kit)は素材から作られ、**それ自体も共有可能な素材**として扱える
- R4.5 事実(日時・会場・人名)と表現(配色・モーション・コピー)を分離して保持する。**事実は捏造しない**という原則がここに依存する

現状の散在(統合対象):

| 素材 | 現在の場所 | 問題 |
|---|---|---|
| イベント素材 | `public/event/<slug>/`(ディスク直置き) | Brandに紐づかない。git除外物 |
| キャンペーンのソース・Brand Kit | `var/campaign-lab/jobs/*.json`(ローカルファイル) | DBに無い。デプロイ先で消える |
| ロゴのマスターSVG | `logo_candidates`(DB) + R2 | ここは正しい |
| 生成画像(Generative Lab) | R2、`logoHash`キー | Brand/ロゴに未接続 |
| ブランドカラー・トークン | `brand_profiles` | ここは正しい |

- R4.6 新規実装は上記を1つのモデルへ寄せる。**ただし一斉移行はしない**(§8)

### R5. UIの不変形: 一覧 + メイン

- R5.1 AssetType配下の画面は「左に一覧(テイク)、右にメイン(選択中のテイク)」
- R5.2 メインには**ゴール(完成物)が常に見えている**。パイプラインの各段はドロワーとして重ねて開き、ゴールを画面から追い出さない
- R5.3 ドロワーの開閉はURLに載る(共有・ブックマーク可能)
- R5.4 進捗は「N件中M件」の実数だけを出す。**推定パーセントや疑似アニメーションを出さない**(止まっているのか動いているのかが分かることを優先)
- R5.5 未充足の表示は**AssetTypeの性格に合わせる**。動画・LPは「フォールバックで成立中」(欠陥ではない)、ガイドラインのような事実提示物では「未確定」として明示する。**同じ見た目で両方を表さない**

> R5.2の「ゴールが常に見える」は16:9の動画では自然だが、ロゴプレゼンのような縦に長いドキュメントでは意味が変わる。**サムネイル一覧+選択ページのプレビュー**という形になる(slide-factoryのDeckPanelがすでにこの形)。

### R6. ロゴプレゼンテーションを複数テイク化する

- R6.1 1つのロゴが**複数のプレゼンテーション**を持てる
- R6.2 新規作成時にプレゼンテーションの型を選ぶ(例: フルガイドライン / 1枚サマリー / SNS向け抜粋)
- R6.3 既存の placement 機構(Composition)はテイク内部の仕組みとして**そのまま残す**

これには壊してはいけない制約がある(§5)。

### R7. LPを動画と同じ形に揃える

- R7.1 `/brands/[id]/lp` をポータル化し、テイク一覧と「＋LPを追加」を持つ
- R7.2 LPのTemplateを導入する。現行のテーマ7種([lib/campaign/themes.ts](../lib/campaign/themes.ts))は**Templateではなく、1つのTemplate内のスタイル選択**として区別する(テーマは後から変更・再レンダリングできる=不変ではない、という現行仕様がその証拠)
- R7.3 既存のLP行(1ブランドに複数存在する例が既にある)を、テイクとして矛盾なく表示できること

### R8. 型の追加コストを小さく保つ

- R8.1 新しいAssetTypeやTemplateの追加は、**レジストリへの追記+レンダラー実装**で済むこと。共通の器(一覧・追加・公開・Run記録)に手を入れる必要がないこと
- R8.2 バナー・ガイドラインを追加するときに、この要件が満たせているかで設計の成否を判定する

## 5. 壊してはいけない制約(最難関)

**`/p/[id]` は公開共有パーマリンクであり、`id` はロゴIDである。** そして `logo_presentations` の主キーは `logo_id` で、1ロゴ=1プレゼンがスキーマに焼き込まれている(`docs/data-model.md §6.5`)。

つまりR6(複数テイク化)は次を必ず伴う:

- C1 `logo_presentations` の主キーを分離する(`id` + `logo_id` FK)。これは実データのある移行
- C2 **既存の `/p/[id]` が指し続ける先を決める**。ロゴには「正典プレゼン」の概念が必要になる
- C3 バニティURL `/[handle]/[slug]` も同様に単一のプレゼンへ解決している。ここも正典を経由させる
- C4 既に共有されたURLが壊れない([docs/account-design.md](account-design.md) の「所有者を含まない壊れないパーマリンク」方針)

**この4点に答えが出るまでR6の実装に入らない。** 動画とLPは opaque な per-take ID(`/c/[id]`、動画アセットID)なので複数テイクと最初から相性が良く、ロゴプレゼンだけが構造的に違う。**したがって着手順はロゴプレゼンを最後にする。**

## 6. 現状の棚卸し

| AssetType | テイク | Template | ポータル | パイプライン | 素材 |
|---|---|---|---|---|---|
| 動画 | ✅ 複数可 | ✅ 2種 | ✅ | 一部(再レンダーUI無し) | ディスク直置き |
| LP | ⚠️ 複数行は存在するが一覧UIが無い | ❌ | ❌ | ✅ CM Maker | ローカルjobファイル |
| ロゴプレゼン | ❌ 1:1(スキーマ制約) | ❌ | ❌ | クライアント解析 | ✅ DB+R2 |
| バナー | ❌ 未実装 | ❌ | ❌ | ❌ | — |
| ガイドライン | ❌ 未実装(kindは存在) | ❌ | ❌ | ❌ | — |

**動画が唯一この形になっている**。よって動画を参照実装として、LP → バナー/ガイドライン → ロゴプレゼンの順に寄せるのが自然。

## 7. 非目標(今回やらないこと)

- Campaignを必須階層にすること。[data-model §0.3](data-model.md#03-campaignを必須階層にしない) の方針を変えない
- 素材ライブラリの一斉移行。既存の動くもの(ロゴのDB+R2、ブランドプロフィール)を壊してまで統一しない
- テイクのバージョン管理・差分マージ。**別テイクを作る**ことで代替する
- slide-factoryの5段をすべてのTemplateに強制すること(R3.1)
- 見た目の統一のために「未充足N件」を全AssetTypeで同じ表示にすること(R5.5)

## 8. 移行の方針

- M1 既存の動く導線を止めない。製品CMはキャンペーン側の実装を唯一の実装として残す(既に `campaignJobId` でリンクしている)
- M2 新旧のIDを共存させる。`videoId` がアセットIDでもキャンペーンjob IDでもよいのと同じ扱いを他AssetTypeでも取る
- M3 スキーマ変更は「増やす」方向を先に、「制約を変える」方向(C1)を後に
- M4 各段階で**その時点のプロダクトが動いている**こと

## 9. この整理で何が良くなるか(判定基準)

1. 新しい成果物の型を追加するとき、共通の器に触らずに済む(R8)
2. 素材を1回入れると、動画・LP・バナーが同じ素材を参照して増える(R4)= 量産効率の本体
3. 「作って終わり」が無くなる。どのテイクも素材を足して作り直せる(R3.3)
4. どこに何があるか、誰が見ても同じ場所に見つかる(R5.1)

## 10. 決めてほしいこと(未決定)

1. **既定テイクの実体化**: 行を持たず合成表示するか(現行の動画方式)、初回オープンで実体化するか。AssetTypeが増えると前者は分岐が増える
2. **`template` の置き場所**: `brand_assets.metadata.template`(現行)か、専用カラム+CHECK制約か。後者は検索と整合性で有利、移行が必要
3. **素材ライブラリの実体**: 新テーブル(`brand_materials` 等)を作るか、既存の `brand_assets` に素材用の `asset_kind` を足して同じ器に載せるか。後者は「成果物と素材が同じテーブル」になる点の是非
4. **ロゴプレゼンの正典**: `/p/[id]` が指す先(C2)。ロゴに `canonical_presentation_id` を持たせるのが素直だが、公開URLの意味が変わる
5. **着手順**: LPポータル化を次にするか、素材ライブラリを先に作るか。前者は見た目の成果が早い、後者は後戻りが少ない
6. **テイクの上限とコスト**: テイクごとにLLM/TTS/レンダリングのコストが発生する。1ブランドあたりの上限や課金の単位をどこに置くか([docs/costs.md](costs.md) と接続)
