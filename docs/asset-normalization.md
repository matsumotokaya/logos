最終更新: 2026-08-19(§11.1 追加・段階7実装: **ロゴ正規化のプロダクト化**。測定は取り込み時に無条件、書き出し=派生素材は承認制。migration 0055 で `ink_ratio` / `trim_width` / `trim_height`)
ステータス: **段階1〜4実装済み・段階5は昇格まで・段階6実装済み(バックフィル実行済み)・段階7実装済み(2026-08-19)・段階8は仕様のみ**。この文書が「アップロードされた素材をどう整え、どう基盤として効かせるか」の正本

## 1. この文書が答える問い

> 雑に入れた素材が、**整理されて出てくる**にはどうすればよいか。
> そして整理された素材が、**次に作るすべてのもの**にどう効くか。

対象は、素材が入ってから成果物に使われるまで——アップロード/スクレーピング → 分類 → 命名 → 保存 → **基盤としての注入** → 再利用 → 書き出し。**成果物そのものの作り方は対象外**(動画は [deliverable-architecture.md](deliverable-architecture.md)、状態の見せ方は [video-state-model.md](video-state-model.md))。

## 2. 位置づけ: 素材の正規化はサービスの第一価値

このサービスを通すと、**あらゆる素材がきちんとしたものになる**。正しい形(透過・トリミング済み)で、正しい場所(スコープ)に、正しい名前で保存され、その後のすべての工程——動画・LP・バナー・書き出し——で使いやすくなる。これを第一の価値として立てる。

理由は2つ。

- **出力の品質は素材の品質で決まる**。編集可能性も素材で決まる——余白だらけのロゴを受け取った動画は、どう組んでも余白だらけになる。テンプレートの精度を上げるほど「素材が悪いせいで綺麗にならない」に突き当たる
- **正規化の副産物がインベントリ=資産になる**。作るたびに素材が散らばるのではなく、**作るたびにブランドの基盤が整っていく**。動画を1本作った会社は、その過程で「自社の正しいロゴと、整理された写真のセット」を手に入れている。次にLPを作るとき、それがもう揃っている

現実のワークフローの問題:

- サイトから拾ってきたロゴは**周囲の余白が大きい**
- 同じロゴに**版が多い**(黒・白・透過・横組み・シンボルのみ)
- どれが「その会社の正しいマーク」なのか、ファイルを見ても分からない

| 行 | 寸法 | 地 | 輝度 | 正しい treatment |
| --- | --- | --- | --- | --- |
| `leopalace21.png`(work) | 800×183 | 透過 | **0.948** | `light` — 既に明るい |
| `leopalace21.jpg`(take) | 800×183 | **地あり** | 0.736 | `light` — 地があるので白抜き禁止 |
| `wealthpark-lab.svg` | 285×52 | 透過 | **0.003** | `knockout` — 暗いマーク |

## 4. 目指す体験

1. 雑に入れる。サイトのURLでも、Slackから落としたフォルダごとでも
2. **勝手に仕分けされる**。人物・製品・ロゴ・背景・資料。ロゴはさらに、黒/白/透過/どの主体のものか
3. **勝手に名前が付く**。中身が分かる名前に。解像度も名前に入る
4. 気に入らなければ**プルダウンで直せる**。分類は決めつけて入れるが、決定権は利用者にある
5. **整理された状態が画面に見える**。絵コンテの下に、この成果物の素材とブランドの基盤が2段で並ぶ
6. **次に作るものに最初から入っている**。マークはブランドから、BGMはテンプレートから自動で入り、貯めた素材はライブラリから選べる。成果物ごとに上書きも、まるごとオフもできる
7. **そのままダウンロードできる**。整理された状態で
8. 書き出したプロジェクトの中も**同じ整理のまま**

「雑に入れたつもりが、綺麗になって出てくる。作るたびに基盤が育つ」。これが体験の全部。

## 5. モデル1: ファイルは絶対軸、情報はテンプレートオントロジー

**この製品は2種類のものを分類しており、それらは軸を共有しない。**(2026-08-16 確認)

| | **ファイル** | **情報** |
| --- | --- | --- |
| 分類の軸 | **1つだけ。サービス全体で共通**、テンプレートと無関係 | **テンプレートごとに違う**(=テンプレートオントロジー) |
| 例 | 人物 / 製品 / 画面 / 場所 / 情景 / ロゴ / 図版 / 資料 / 質感 | イベント: 会場・参加費・プログラム・登壇者<br>LP: 料金プラン・お客様の声・FAQ<br>製品CM: 5シーンの台本 |
| 実体 | `brand_materials.category`(§5.1) | Takeの `brief`(+ 成果物を越えるものは BrandKnowledge) |
| なぜそうか | 人物写真は、動画でもLPでもバナーでも人物写真。**成果物と無関係に真** | 共通の一覧を作ると、全テンプレートが他のテンプレートの項目を持ち回ることになる |

**判定基準は「開けるものか、読むものか」。** 画像・PDF・音声のように**開ける**なら素材で、上の絶対軸で分類する。価格・氏名・日時・会場名のように**読むだけ**なら情報で、テンプレートのbriefが持つ。

`brand_materials` はバイト列の無い行を作れない([0028](../supabase/migrations/0028_brand_materials.sql) の `materials_has_body`)。だから「3,000円」にカテゴリーを与えようとすると、**ラベルを貼るためだけに中身が「3,000円」のファイルをR2へ置く**ことになる——これが§5.2で言う「その値を入れるためのファイルを発明する」の意味。以後、価格を直すたびにR2オブジェクトが増え、参加費を読むのに検索とダウンロードが要る。`brief.schedule.fee` ならJSONの1フィールドで済む。

**同じ現実のものが両側に分かれるのは正常。** イベントの会場は、`brief.schedule.venue` の文字列「WealthPark Lab 東京オフィス」**と**、`category='place'` の建物の写真の**両方**として存在する。重複ではない——一方は事実、一方はファイルで、画面に映せるのは後者だけ。

### 5.0 ファイルをどのスロットに置くか(これもテンプレート側)

「この動画のキービジュアルは何か」は**テンプレートオントロジーの一部**。だから `key-visual` は §5.1 の語彙に入っていない——それはスロットの名前であって、写っているものの名前ではない。同じ写真が、あるキャンペーンではキービジュアルで、別のキャンペーンでは背景になる。

- **ファイルが何か**は素材の行が持ち、**一度決めれば成果物を越えて有効**
- **どのスロットに置くか**は `brief` のスロットと `take_inputs.role` が持ち、**成果物ごとに変わる**

素材側に焼き付けてはいけないのは後者。逆に「これは人物の写真だ」を毎回LLMに聞き直すのは無駄で、間違えると絵が壊れる(§3のleopalace21)。

- ファイルの軸は `brand_materials.category`(migration 0053)。既存の `kind` は**媒体の種別**(logo / photo / audio / document …=バイト列の扱い方)として保つ。1つのファイルへの2つの問い——`kind` は「どう復号して描くか」、`category` は「何が写っているか」。`kind` を置き換えない理由は、CHECK制約と既存コードの読み手が全部 `kind` を見ているため——置き換えは移行の割に得るものが無い
- スロットは使う側(`brief`、`take_inputs.role`)が持つ。**現状もそうなっている**ので変えない
- **手で直せる**。分類は決めつけて入れる(空欄にしない)が、プルダウンで覆せる。`category_source` が `inferred`(実行が上書きしてよい)か `user`(実行は二度と触らない)を持つ——ナレーションの `source: "human"` と同じ契約で、**決めつけてよいのは、直した結果が残るときだけ**

### 5.1 語彙(2026-08-16 決定・コードの正本は [lib/materials/category.ts](../lib/materials/category.ts))

**呼び名はすべて「〜の写真」「〜の画像」で終わる。** 「場所」ではなく「場所の写真」。前者は会場フィールドのことに読めるが、後者はファイル以外に読みようがない——§5の区別を、仕様書を読んでいない人にも呼び名だけで伝えるため。

| --- | --- | --- | --- |
| `person` | 人物の写真 | 人物の顔が主役 | `miyao.jpg` `kato.jpg` `onishi.jpg`(登壇者3名) |
| `product` | 製品・サービスの写真 | 製品・現物そのもの。パッケージ・提供している料理 | (この案件には無い) |

| `place` | 場所の写真 | 会場・店舗・オフィス・物件の外観や内観 | 蔵・会場の写真 |
| `scenery` | 情景の写真 | 人も物も主役でない雰囲気カット。地に敷ける | `pour-lanterns.jpg` `slate.jpg` |

**この表は増える前提で設計している**が、**増えるのは遅い**。新しいテンプレートが持ち込むのはたいてい新しい**情報**(料金プラン・FAQ・お客様の声)で、それは§5の表の右側で増えるのでこの表を揺らさない。**本当に新しい種類のファイル**が要るのは稀。増やすときは[コードの表](../lib/materials/category.ts)1行 + migration 1行で、**既に保存された値の意味は変わらない**。

動画だけを見て決めると `product` / `screen` が落ちるので、最初から入れてある。

### 5.2 カテゴリーに入れてはいけないもの

増やすときに毎回戻ってくる問いなので、答えを書いておく。**ここを間違えるとモデルが静かに壊れる。**

| 入れたくなるもの | 正しい居場所 | なぜ |
| --- | --- | --- |
| **価格・プラン、お客様の声の本文、3つのポイント、タグライン、説明文、会場名、開催日、氏名** | **テンプレートのbrief**。イベントの参加費は `brief.schedule.fee`([remotion/event/types.ts](../remotion/event/types.ts))、LPの料金は `kit.pricing.plans`([lib/campaign/schema.ts](../lib/campaign/schema.ts))。成果物を越えて持ち回るものは BrandKnowledge(`offer.*` / `evidence.*` / `identity.*`。[data-model.md §3](data-model.md)) | **開けるものではなく読むもの**。下記 |
| **バナー・サムネイルの解像度違い** | **派生素材**(`derived_from_material_id`)+ 測定済み `width`(§6・§11) | 同じ写真の別サイズは**同じ内容**。サイズで分類すると1枚の写真が3つの別物になる |
| **キービジュアル / 提供マーク / 登壇者の写真** | **briefのスロット**(§5.0) | スロットの名前であって、写っているものの名前ではない |

**「その値を入れるためのファイルを発明する」とは。** `brand_materials` はバイト列の無い行を作れない(0028 の `materials_has_body`)。だから `category` に `price` を足すには価格の**行**が要り、行にはファイルが要る。「3,000円」はファイルではないので、**ラベルを貼るためだけに中身が「3,000円」のテキストをR2へ置く**ことになる。その結果:

- 価格を直すたびに**R2に新しいオブジェクトが増える**(内容アドレスなので、文字が変われば別ファイル)
- 参加費を読むのに、素材を検索し、R2から本体を取り、中身を読む必要がある
- `brief.schedule.fee` なら、JSONの1フィールドを読むだけ

LPが必要とする「価格」「お客様の声」は**ファイルの軸ではなくテンプレートオントロジーの側**で増える。2つが別々に増えるので、片方の追加がもう片方を揺らさない——これが「そんなに大きな修正にはならない」ことの根拠。

### 5.3 分類は誰がするか

構造化LLMが画像を読むときに**2つの軸を別々に答える**([lib/event-cm/structure.ts](../lib/event-cm/structure.ts) の `ImageReading`)。

- `role` = **この動画での使い道**(`speaker-portrait` / `key-visual` / `venue` …)。配置([place-images.ts](../lib/event-cm/place-images.ts))が読む。event-cm の語彙のままでよい
- `category` = **写っているもの**。素材の行に残る。テンプレート非依存

以前は1語で両方を答えさせていた。だから `key-visual`(使い道)と `venue`(内容)が同じ列に並び、`product` が存在しなかった。**同じ写真が「この動画ではキービジュアル」かつ「内容は製品」であることは普通に起きる**ので、1語では足りない。

`category` が空のまま返ってきた実行のために、`role` からの決定論的な翻訳を残してある(`categoryFromImageRole`)。`key-visual` / `scene-photo` はどちらも `scenery` に落ちる——**どちらも「何が写っているか」を言っていない**ので、内容としては情景と答えるほかない。配置は元の `role` を読み続けるので、この丸めで失うものはない。`unreadable` は `other` ではなく **null**(「見たが何でもなかった」と「分からなかった」は別)。

## 6. ロゴが持つ下位属性

ロゴだけは追加で属性を持つ。ロゴは「1社に1ファイル」ではないため。

| 属性 | 値 | 測り方 |
| --- | --- | --- |
| **地の有無** | 透過 / 地あり | `measureArtwork()` が既に測っている(`opaque`) |
| **明度** | 暗いマーク / 明るいマーク | 同上(`luminance`) |
| **主体** | どの会社・事業・製品・イベントのものか | ロゴ正本エンティティ(`logo_id`)と繋ぐ |
| **解像度** | 幅×高さ、またはベクター | **`width`/`height` を埋める**(いま全行null) |
| **絵柄の位置と量** | 絵柄自身の箱(`trim_width`/`trim_height`)と、その箱の中のインク占有率(`ink_ratio`) | `measureMark()` が測る(migration 0055・2026-08-19)。**余白の割合**と**光学的な重さ**の両方がここから出る(§11) |
| **構成** | 横組み / 縦組み / シンボルのみ | 判定は後回しでよい。人が直せれば足りる |

**測定の正本は [lib/materials/measure.ts](../lib/materials/measure.ts)**(2026-08-16 実装。テストは [measure.test.ts](../lib/materials/measure.test.ts))。抽出段が持っていた `measureArtwork` をここへ引き上げたので、**取り込みが行へ書く値と、抽出段が読み直す値は同じ実装から出る**。

- **測らないことは失敗ではない**。音声・PDF・デコードできない画像は `UNMEASURED`(全部 null)を返し、**例外を投げない**——読めない素材も素材なので、登録は続く
- **null は false ではない**。「測っていない」と「透過していない」を混同すると、白板バグがそのまま戻る。読む側は3値として扱う
- migration 0052 が足すのは `opaque` / `luminance` の2列だけ(`width`/`height`/`source_url` は 0028 からの既存列)。migration 0055 が `ink_ratio` / `trim_width` / `trim_height` を同じ場所に足す。**`aspect` は列にしない**——`trim_width / trim_height` そのものなので、計算元の隣に計算結果を置くと後で食い違う(§8.1 と同じ判断)

## 7. モデル2: 2層の注入(ブランドの基盤と、成果物の素材)

素材は成果物へ**2層**で届く。この解決規則が、動画・LP・バナー・その他マーケティングツールすべてに共通の基盤になる。

```text
第1層  ブランドの基盤(base)          scope='brand' の素材 + canonicalロゴ + BrandKnowledge採用値
         │  成果物の作成時に「インストール」される(スロットへ投影+pin)
         ▼
第2層  この成果物の素材(override)    scope='take'/'work' の素材、その成果物での役割割り当て
         │  同じ役割を指せば基盤を上書きする。指さなければただ追加される
         ▼
       成果物(Take の brief スロット + take_inputs)
```

### 7.0 基盤は「すべての営業アセットの手前」にある(2026-08-17 確認)

**ブランドの基盤は動画の基盤ではない。** LP・バナー・動画・その先のすべての成果物より**手前**にある層で、だからそこに置けるのは「**この会社について真であること**」だけ。成果物の種類ごとの初期値は、その1つ下の**テンプレート**が持つ。

```
ブランドの基盤 ── すべての営業アセットが共有する。会社について真であること
      │          マーク / 配色 / 書体 / 声のトーン / 自社・製品の写真
      ▼
テンプレートの初期値 ── その種類の成果物にだけ意味があること
      │          動画: BGM・尺・アートディレクション
      │          LP: セクション構成・テンプレート
      │          バナー: 比率・サイズ展開
      ▼
成果物(Take) ── この1本で決めたこと
```

**どちらの層に属するかは、1つの問いで決まる: その値はLPでも意味を持つか。**

| もの | LPでも意味を持つか | 置き場 |
| --- | --- | --- |
| マーク | ○ LPにもバナーにも載る | **ブランド** |
| 配色・書体 | ○ | **ブランド**(ファイルではなく情報なので BrandKnowledge) |
| 製品・自社の写真 | ○ LPのヒーローにも使う | **ブランド**(ライブラリ) |
| **BGM** | **× LPに音楽は無い** | **テンプレート** |
| 尺・アスペクト比 | × | **テンプレート** |

**これが「ブランドのBGM」が誤りだった本当の理由。** 「ブランドは音楽を持たない」だけでなく、**基盤はすべての成果物の手前にある層なので、動画にしか意味を持たない概念を置く場所ではない**。動画だけを見ていると気づけず、「LPにBGMはあるか」と問うた瞬間に答えが出る。§5 の「ファイルは絶対軸・情報はテンプレートオントロジー」と同じ形の間違いを、既定値の側で繰り返していた。

**声は3つ目の層にある。** `DEFAULT_VOICE_PRESET`([lib/voice/voices.ts](../lib/voice/voices.ts) の「標準」)は**テンプレートにも寄らないシステム全体の既定**で、`brief.narrator` が未指定のときに使われる。ブランドが声を決めようがなく、テンプレートごとに変える理由も無いなら、既定は1つで足りる。**層は必要な数だけ**で、増やすのは意味が分かれたときだけ。

### 7.1 規則

- **基盤は作成時にインストールされる**。新しい Take(動画・LP・バナー)を作ると、ブランドの基盤——canonicalロゴ、ブランドのBGM、基調のキービジュアル等——が該当スロットへ投影され、`take_inputs` に pin される。**レンダー時に再解決はしない**(既存契約 [data-model.md §4](data-model.md) のまま)。「その時点の基盤」が固定されるので、後からブランド側を差し替えても既存の成果物は黙って変わらない
- **上書きは役割の単位で起きる**。成果物側でアップロードした素材が基盤と同じ役割(提供マーク・BGM等)を指せば、その役割ではそちらが使われる。基盤の pin は残り、由来 `brand` として記録され続ける(インベントリが「上書き中」と言える)
- **重ならないものは上書きしない**。写真や企画書は基盤に対応物が無いので、ただその成果物の素材として加わる。上書きは衝突したときだけの概念
- **基盤はまるごとオフにできる**。コラボイベントで自社のトンマナを出さない、といった場合。オフは Take 単位の決定として brief の provenance に記録する(読み上げのオフと同じ形——ポインタを外すだけだと次の実行が勝手に戻す)。オフのとき各スロットは**設計済みフォールバック**へ落ちる(基盤の次の候補へは落ちない)
- **基盤には2種類ある**。ファイル(ロゴ・写真・BGM = `brand_materials`)と、値(配色・書体・声のトーン = `brand_knowledge_values`)。この文書はファイル側の正本。値側は「brief作成時に必要なKnowledgeだけを投影する」という既存契約([data-model.md §3](data-model.md))が既に同じ形をしているので、オフ/上書きのUXだけをファイル側と揃える

### 7.2 何が基盤に入るか(2026-08-17 修正)

**第2版はここを間違えていた。** 「ロゴ以外(BGM・基調キービジュアル等)はブランドの素材ライブラリでスロットに指名する」と書き、その指名方法を未決定事項に挙げていた。**ブランドはBGMを持たない。**

ブランドが作られるときに入るのは、**ロゴ・基本情報・デザインガイドライン**(配色・書体・声のトーン)だけ。URLや資料から抽出できるのもそこまでで、**音楽はどこからも出てこない**。[lib/assets/defaults.ts](../lib/assets/defaults.ts) 自身がそう書いている——「Nobody uploads a soundtrack; they expect one」。ロゴからの類推で「ブランドのBGM」を発明したのが誤りだった。

正しくは:

| 何 | どこが持つか | いまの状態 |
| --- | --- | --- |
| **マーク** | ブランド。`logos` + primary `logo_candidates` が「その会社の正しいマーク」 | **動く**。`seedEventCmFromBrand` が新しい動画へ入れる |
| **配色・書体・声のトーン** | ブランド。ただし**ファイルではなく情報**なので `brand_knowledge_values`(§5) | 動く。brief作成時に投影される |
| **BGM** | **テンプレート**。[lib/templates/catalog.ts](../lib/templates/catalog.ts) の `defaultBgm` | **動く**(2026-08-17)。新規作成時に一律で入る |
| **写真・資料** | ブランドの**ライブラリ**。指名という概念を持たない | 昇格で貯まる。使うときは選ぶ |

**だから「基盤スロットの指名」という仕組みは要らない。** 自動で入るものはすべて既に持ち主が決まっており(マークはブランド、BGMはテンプレート)、残りは「ライブラリから選ぶ」もの——選ぶものに既定は要らない。

### 7.2.0 空のスロットは見えていなければならない(2026-08-17)

**ブランドの持ちものは「名前の付いたスロット」として並べ、無いものは「未指定」と言う。** 実装の正本は [components/brand/BrandAssetSlots.tsx](../components/brand/BrandAssetSlots.tsx)。

キービジュアルを持たないブランドのページには、これまで**キービジュアルの節そのものが無かった**。すると画面は「まだ指定していない」と「この製品にはその概念が無い」を区別できない。**不足を名指しするのはこの製品の既存の姿勢**(パイプラインの「不足」欄=「この一覧が、次に取りに行くものです」)で、ブランドアセットだけがそれをしていなかった。

- **同じコンポーネントをブランドページと動画ページの両方で使う**。ブランドページは会社が持っているもの、動画ページは**この動画が実際に使っているもの**を、同じ行・同じ順・同じ言葉で答える。**動画独自のブランド情報**——自社ではなくパートナーのマークを使っている、この動画だけのキービジュアルがある——が、2つの違う形の画面を見比べずに読める
- **未指定は琥珀にしない**。破線と静かな灰色。キービジュアルを出していないブランドは警告状態ではなく、テンプレートは**まさにその場合のために**設計代替(墨の地・金の粒子)を描く
- 動画側は `eventCmFilm(brief).drawn` を読む。だから**基盤をオフにした動画のスロットは空になる**——画面が映像と食い違わない

**ブランドのキービジュアルは `brand_materials.kind = 'keyvisual'`。** `category` ではない理由は、`category` が**写っているもの**だから——日本酒の物撮りは、誰かがキービジュアルに指名しようがしまいが `product` の写真であり続ける。`kind` は 0028 から役割寄りの値を持っており(`logo` も `font` も媒体ではなく役割)、`keyvisual` はCHECK制約に**最初から在って誰も書いていなかった**。再利用すればmigrationも第3の軸も要らない。

### 7.2.1 既定値の3層(2026-08-17 決定)

| 層 | 誰が持つ | いま在るもの | コード |
| --- | --- | --- | --- |
| **1. ブランド** | この会社について真であること | マーク | `logos` + primary `logo_candidates` → `seedEventCmFromBrand` |
| | | 配色・書体 | `brand_knowledge_values` |
| | | キービジュアル | **たいてい無い**(ブランドは写真を持って来ない) |
| **2. テンプレート** | その種類の成果物にだけ意味があること | BGM | `TemplateEntry.defaultBgm` |
| | | 既定の画像 | `TemplateEntry.defaultVisuals`(**受け皿のみ・画像はこれから**) |
| **3. システム** | 層を分ける意味が無いもの | 読み上げの声 | `DEFAULT_VOICE_PRESET`(「標準」) |
| **4. 設計代替** | どれも無いとき | 墨の地・金の粒子・明朝のクレジット | コンポジション |

**4層目があるから上の層は空でよい。** 素材ゼロでも完成した動画が出るのが event テンプレートの要件なので、テンプレートの既定画像が未用意でも穴にはならない(墨の地が出る)。だから**画像が届いたらプールに1行足して `defaultVisuals` に1行書くだけ**で、テンプレートもコンポジションも触らない。

キービジュアルは1層目に**在り得る**(サイトから取得できたり、利用者が足したりする)。ただし**在ることの方が稀**なので、2層目を用意しておく必要がある——これが `defaultVisuals` を先に作った理由。

### 7.2.2 BGMはテンプレートが持つ(2026-08-17 決定)

**映画の種類が音楽を決める**のであって、誰が作るかではない。イベント告知と製品CMが違う曲を欲しがるのはテンプレートの性質で、顧客の業種の性質ではない。

- 正本は `TemplateEntry.defaultBgm`(プールの asset id)。解決は [lib/assets/defaults.ts](../lib/assets/defaults.ts) の `templateBgm()`
- **新規作成時に一律で入る**。以前は `defaultAsset("bgm", archetype.tone)` で、`tone` はブランドの業種由来だった——**同じテンプレートの2本が、誰も選んでいない理由で違う曲で始まり得た**
- **現在の割り当てはプレースホルダー**。プールに2曲しかないので、event-promo と event-cm が和モダン、product-cm がコーポレート。**適切な曲は後で用意する**。差し替えは台帳の1フィールドを書き換えるだけで、**既存のTakeは動かない**(briefは再シードされないため)
- 宣言が無い/プールが失った場合は**無音**。別の曲で埋めない(テンプレートにとって無音は設計された状態)

### 7.3 いま一番欠けているもの

このモデルの DB 基盤(3スコープ・widen-only の昇格trigger・RLS)は migration 0028 で既に存在する。**実在しないのはブランドの基盤そのもの**——brand スコープの素材が現在1行しかない。基盤を実在させる経路は3つあり、どれも既存の仕組みの延長:

1. **昇格**。Take の素材を「これはブランドの正だ」とワンタップで brand へ広げる(trigger は widen-only を既に保証している)
2. **ロゴ正本との接続**。`promoteLogoToMaterial` の既存経路
3. **取り込み時の提案**。ロゴと判定された素材は「ブランドの基盤に登録しますか」と聞く(将来のスクレーピング取り込みもここへ合流)

## 8. 名前が正本(ファイル名ドリブン)

**フォルダは便宜、名前は契約。** 極端に言えばフォルダが無くても、名前が長ければ用は足りる。名前だけで意味が通るなら、ZIPを解いた人も、grepする人も、AIエージェントも同じ理解にたどり着く。

命名の骨子(案):

```
assets/logo/wealthpark-lab_mark_transparent_dark_512w.png
assets/logo/leopalace21_wordmark_plate_light_800w.jpg
assets/person/miyao-yoshiaki_portrait_1600w.jpg
assets/keyvisual/sake-tasting_1920w.jpg
assets/document/flyer-2026-09-18.pdf
assets/audio/narration_ja_female-1.wav
```

- **`<base>_<属性>_<幅>.<拡張子>`**。属性は**測ったものだけ**入れる
- **幅を名前に入れる**。「大・中・小」はアップロード時点では決められないが、幅は測れば分かる。後から人が「これが大きい方」と判断できる
- ベクターは幅を持たないので `vector` と書く
- **拡張子を必ず付ける**。以前は書き出しに拡張子の無いファイルが出ていた(R2キーのbasenameがチェックサムのため)
- 日本語名は**付けない**。ZIPのファイル名表はUTF-8フラグを立てないので、`unzip` が展開を拒む([lib/export/naming.ts](../lib/export/naming.ts) に同じ理由の先例がある)。ASCIIに落ちない名前は、**システムが作った素材なら何か分かっている**ので語を当てる(`貼り付けたテキスト`→`note.txt`、`イベント紹介動画の読み上げ`→`narration.wav`)

### 8.1 保存せず、導出する(2026-08-16 決定・第1版から変更)

第1版は「`label` を正規化名に書き換え、元名を `provenance.originalFilename` へ退避する」としていた。**実装して逆にした。**

名前は**行が既に持っている事実の純粋な関数**——届いたときのファイル名・分類・測定値・メディアタイプ——なので、その出力を入力の隣に保存すると**2つ目の正本ができ、分類を直した瞬間に古くなる**。情景から人物へ直した写真はフォルダも名前も変わるべきだが、保存した `label` は誰かが書き直すまで古いままになる。導出にすれば**直すことがそのままリネーム**になり、画面も書き出しも同時に変わる。プルダウンが約束しているのはその挙動。migration もバックフィルも要らない。

- **正本は [lib/materials/naming.ts](../lib/materials/naming.ts)**(`materialFileName` / `materialFolder` / `materialPath` / `uniqueMaterialPaths`)
- **`label` は「届いたときの名前」のまま**。捨てない——ドラッグしたファイルを人が見つける手がかりはそれなので、一覧は正規化名の下に「元: …」を出す(変わったときだけ)
- **同じ名前になる2件は連番で分ける**。ZIPで片方が黙って消える方がひどいので

### 8.2 意味は発明しない(§13-3 の答え)

決定論だけで作り、**LLMは使わない**。`AdobeStock_1894358160` に `sake-tasting` と名付けるのは正規化ではなく推測で、**間違っても静かで、しかも取り返した感じがしない**操作になる。意味の無い名前が正直に元のままである方が、もっともらしい名前が間違っているよりよい。

名前に入るのはすべて事実である:

| 部分 | 出どころ |
| --- | --- |
| base | アップロードされたファイル名(ASCII化) |
| 属性 | **測定値**(マークの地の有無・明度) |
| 幅 | **測定値** |
| 拡張子 | メディアタイプ |

**測っていない属性は名乗らない。** `opaque` が null のマークに `transparent` と書くのは、誰も取っていない測定をファイル名に書くこと——白板バグと同じ間違いを名前で繰り返すことになる。

### 内容アドレスと人間可読名は両立させる

いまR2キーは**内容アドレス**(チェックサム)で、これは重複排除と不変性のために正しい。一方で人が読む名前は同じバイト列に対して**複数あり得る**(同じ写真が別の動画で別の役割を持つ)。

だから**R2キーは内容アドレスのまま変えない**。人間可読名は**行が持つ**。書き出し・ダウンロード・一覧が読むのは行の名前で、保存の同一性はチェックサムが握る。**名前を変えてもバイトは動かない**、が守るべき性質。

## 9. インベントリUI(2026-08-16 決定)

素材の整理は**画面に見えて初めて価値になる**。置き場所は2面、実装は1つ。

### 9.1 絵コンテの下: 素材インベントリ

動画詳細(将来はLP詳細も)の絵コンテの下に**「素材」セクション**を置く。**2段の構え**で、素材の注入が2層であることをそのまま可視化する:

```
素材
├─ この動画の素材            (scope=take / work。この成果物に固定されたもの)
│    ├─ logo/     leopalace21_wordmark_plate_light_800w.jpg   [ロゴ] [資料から]  → シーン8
│    ├─ person/   miyao-yoshiaki_portrait_1600w.jpg           [人物] [アップロード] → シーン6
│    ├─ keyvisual/ sake-tasting_1920w.jpg                     [キービジュアル]   → シーン3
│    └─ document/ flyer-2026-09-18.pdf                        [資料] (画面には出ない)
└─ ブランドの基盤             (scope=brand + canonicalロゴ)                [オン/オフ]
     ├─ logo/    wealthpark-lab_mark_transparent_dark_vector.svg [正マーク] → シーン1・8・9
     └─ audio/   (基盤BGMなし — システム既定を使用中)
```

- **ディレクトリ状に見せる**。§8 の命名の `assets/<種別>/` グルーピングをそのまま画面の構造にする。画面とZIPと書き出しが同じ地図を持つ
- 各行は**正規化名・種別チップ・由来チップ・使用先**(どのシーン/セクションに載っているか= `take_inputs` の role と brief スロットから導出)を出す。使われていない素材は使用先が空欄——それは異常ではなく「まだ割り当てていない」という正常な状態
- **上書きは基盤の行に言わせる**。「この動画ではコラボ先のBGMを使用中(基盤のBGMを上書き)」のように、負けた側に理由が出る。黙って消すと「基盤が壊れた」に見える
- **基盤セクションのヘッダにオン/オフ**(§7.1)。オフのときは段全体がグレーになり「この動画はブランドの基盤を使いません」と言う
- 分類(§5 の `category`)と名前は**その場でプルダウン/インラインで直せる**。決めつけて入れ、決定権は利用者
- 昇格(「ブランドの基盤へ」)もこの行のメニューから。widen-only は DB trigger が保証済み
- **読み取り専用にしない**が、盤面(絵コンテ)との役割分担は守る: 絵コンテは「どこに載るか」、インベントリは「何を持っているか」。役割の割り当て(差し替え)は従来どおりシーンの `FactList` から行い、インベントリからは素材そのものの属性(名前・分類・スコープ)だけを直す。2つの編集面で同じことをできるようにしない

### 9.2 パイプラインのマッピング段ドロワー

ドロワー内の既存の素材一覧を**同じインベントリコンポーネント**に置き換える。絵コンテ下とドロワーが別実装になると、必ず食い違う(一覧と詳細の `videoState` 食い違いと同じ轍)。

### 9.3 ブランドの素材ライブラリ(後続)

`/brands/[id]` 配下にブランド素材ライブラリの画面を立てる(基盤スロットの指名・全成果物を横断した素材の一覧・ダウンロード)。これは §14 の後半の段。まず Take の中で2段が見えることが先——利用者が最初に素材と出会うのは成果物を作っている最中だから。

## 10. 書き出し・ダウンロードに同じ整理が出る

[プロジェクト書き出し](../README.md#プロジェクトデータの書き出しロックインしない)が吐く `public/materials/<uuid>/<checksum>` は、いま**第三者にとって読めない**。正規化後は:

```
public/assets/logo/wealthpark-lab_mark_transparent_dark_512w.svg
public/assets/person/miyao-yoshiaki_portrait_1600w.jpg
```

`props.json` の参照もこのパスになる。さらにインベントリから**素材だけのZIPダウンロード**も同じ構造で出す(プロジェクト書き出しの部分集合。「サイトをスクレーピングして素材を集め、綺麗になった素材だけを持ち出して自分でコーディングする」という道筋の出口)。

**整理された状態のまま持ち出せることが、正規化の意味の半分**——手元で続きを作る人が、どのファイルが何かを名前だけで判断できる。

## 11. 余白のトリミング(2026-08-18 決定・Freehand Labで実証済み)

サイトから拾ったロゴは余白が過大なことが多く、そのまま組むと**版面の設計が効かない**(実際 event-cm のマークは `scale` で個別に逃がしている)。

- **画像の加工は取り込み時に行う。描画時のフィルタではやらない。** これは既に確立した原則で、「フィルタは板を切り抜けない——マークの上に塗るだけ」という失敗から来ている(commit `1c95bdf`)。トリミングも同じ側に置く
- **決定論でできることはLLMに聞かない**。余白の除去は α または輝度の境界を走査すれば求まる。`sharp` は既に使っていて、[labs/event/scripts/prepare-assets.mjs](../labs/event/scripts/prepare-assets.mjs) に前例がある
- **LLMが要るのは判断が要るところだけ**: 「この余白はデザインの一部か、切り落としてよい余白か」「この画像に写っているのはロゴか、ロゴが写り込んだ写真か」
- **原本は消さない**。トリミング結果は**派生素材**として作る。`derived_from_material_id` 列が既にあり、使う側がいない——ここが最初の使い手になる。切りすぎたときに戻れることが、自動でトリミングしてよい条件

**実装の種は [labs/freehand/scripts/normalize-marks.mjs](../labs/freehand/scripts/normalize-marks.mjs) にある**(2026-08-18・「世界が恋する日本酒」の自由制作で実測)。3つの操作が確定した:

1. **白地プレート剥がし**(`plate:"white"`)。不透明な白地に載ったロゴ(Miss SAKEの白枠webpが実例)は、**白からの距離をアルファに変換**してから切る。エッジのアンチエイリアスが保たれる
2. **アルファboxトリミング**。α境界の走査(閾値12)
3. **インク面積スケール**。トリミングだけでは足りない——2段組のロックアップを1行のワードマークと同じ高さに揃えると格下に見える。**デザイナーが目で合わせているのはインクの量**で、`インク占有率 × 縦横比` から各マークの相対スケールが導出できる(面積は高さの2乗で効くので補正は平方根+減衰0.5+上下限)。この値は `opaque` / `luminance` と同じ「取り込み時に1回測って行に残す」測定列に入る

**体験も決まった(依頼者・2026-08-18)**: アップロード時に**提案して人が承認する**(§13-5は解決)。「このロゴは余白が大きい/使いづらい形式なので、**正規化バージョンも作成しますか?**」→ Yes で**原本と並んで**派生素材が保存され、LP・動画・モックアップのどこからでも使える。**このツールはロゴ専用ではなく、プロダクト全体のアップロード経路で「ロゴっぽい画像」に同じ処理が効く**(動画の素材として投入されたロゴにも同じコンポーネントが働く)。ブランドアセットを上げたら綺麗に再利用可能な形で保管される——このプロダクトの根底の機能に位置づける。

### 11.1 実装(2026-08-19・段階7)

**測定は無条件、書き出しは承認制。** ここが分かれている理由は、費用と取り消しやすさが違うから——測るのは1回のデコードで済み間違っても害が無い。ファイルを書くのは取り消せる形(派生)にしないと offer できない。

| 層 | 正本 | 何をするか |
| --- | --- | --- |
| 測る(純粋) | [lib/materials/optical.ts](../lib/materials/optical.ts) | インク量→**行ごとのスケール**(`opticalScales`)、測定値→**提案するか**(`normalizationProposal`)。sharp も `server-only` も持たないので、画面とサーバーが同じ関数で同じ判断をする |
| 測る(画素) | [lib/materials/normalize.ts](../lib/materials/normalize.ts) | 白地プレート剥がし・αboxの走査・インク占有率(`measureMark`)、承認後の切り出し(`normalizeMark`) |
| 残す | migration 0055 + [measure.ts](../lib/materials/measure.ts) | 取り込み3経路すべてが `ink_ratio` / `trim_width` / `trim_height` を行へ書く(`measurementColumns` に足しただけ) |
| 提案する | [MaterialInventory.tsx](../components/materials/MaterialInventory.tsx) | インベントリの各行。**押せるのは1回**——派生が既にある行は聞かない |
| 作る | `POST /api/brands/[id]/materials/[materialId]/normalize` | 派生行(`source_kind='derived'` + `derived_from_material_id`)、原本と同じスコープ、原本のピン先すべてに `role='normalized'` でピン、**原本を指していたブリーフを派生へ差し替える** |
| 使う | [place-images.ts](../lib/event-cm/place-images.ts) | 映像に載せるのは派生(`normalizedId`)、モデルに読ませるのは原本。**マークが2つ以上並んだらインク量で大きさを揃える**(`logos[].scale`) |

**測定はkindで絞らない。** 取り込み時の `kind` はメディアタイプから出るので、パートナーのロゴを webp で受け取ると `photo` になる——実データ(`Miss-sake_赤ロゴ-1536x542.webp`)がまさにそれで、kindで絞ると**この機能が書かれた理由の素材だけを外す**。測定は全画像に走り、絞るのは提案の側。

**提案の引き金は2つあり、片方は測定だけで決まり、もう片方は決まらない。**

| 引き金 | 条件 | なぜその条件か |
| --- | --- | --- |
| **余白** | 絵柄がフレームの **70%未満** | フレームの92%が空なのは、行が何と言おうと写真ではない。だから測定だけで提案してよい。**kindが `photo` のまま届いたマークを拾うのはこちら** |
| **白地** | `opaque` かつ(**マークだと分かっている** or 余白が既に証明した) | `opaque` は「アルファが無い」であり、それはすべてのJPEGについて真。写真から白を剥がすと空が消える。**不透明なフレームの中に絵柄が収まっているなら、それは板**なので、余白の側が証明したときだけ測定で名乗ってよい |

**この境界は実データで決めた(2026-08-19・45件)**。緩い版(`opaque` 単独 + `ink_ratio < 0.6`)では **9件に提案が出て、うち7件が写真**だった——縁が白いだけのストックフォトが引っかかる。締めた版では **2件だけ**で、両方とも本物:

| 素材 | 何が起きているか |
| --- | --- |
| `Miss-sake_赤ロゴ-1536x542.webp` | 1536×542 のフレームに **351×192 の絵柄(8%)**。白地+余白の両方 |
| `leopalace21.jpg` | JPEGで届いた企業ロゴ。余白は無い(fill 1.0)が `category='mark'` が付いているので**板として名乗れる**——白い長方形バグの当事者そのもの |

**分類を直すと提案が現れる。** 余白の無い白地マークは、測定だけでは写真と区別できない。プルダウンで「マーク」を選んだ瞬間に提案が出るのは偶然ではなく、§5.3「分類は誰がするか」の答えがここで効いている形。

**SVGには提案しない。** viewBox が絵柄であり、切るためにラスタライズすると拡大できる唯一の形式を捨てることになる。

**差し替えたら「未反映」になる。** 承認は `brief` を書き換え、`baked_brief` は触らない。動画は次に実行するまで前のマークで再生される——これは [video-state-model.md](video-state-model.md) の3層の鎖が設計どおりに動いている姿で、琥珀は異常ではない。

**再実行で承認は取り消されない。** マッピング段は原本のIDで読み取り結果を受け取るので、`normalizedId` を見ないと毎回余白だらけの原本に戻す。「押したボタンが次の実行で消える」を作らないための配線。

**実測(2026-08-19・sake-2026の5マーク)**: 移植はラボの判定値を再現した(`ink_ratio` 0.2230 / ラボ 0.2231、`scale` 0.716 / 0.725 など)。基準線は [lib/materials/optical.test.ts](../lib/materials/optical.test.ts) に固定してあるので、計算を変えて数字が動けば**依頼者が既に見て承認した判断**を変えたことがテストで分かる。

**既知の穴**: Takeを削除して素材を `promote` すると、**正規化版は昇格せずに消える**(`delete_take` の昇格対象は `upload` / `url_fetch` / `ai_generated` で、`derived` を含まない)。原本は残るので1クリックで作り直せるが、昇格した原本が正規化版を失うのは正しくない。R2のオブジェクトは回収されるので**漏れはしない**。

## 12. スコープと昇格(インベントリとしての再利用)

素材は3スコープを持つ(`take` / `work` / `brand`)。正規化された素材は**上のスコープに昇格するほど価値が出る**——同じロゴを次の動画でも、LPでも使える。§7 の2層モデルは、この昇格の**行き先**(brand = 基盤)に意味を与えるもの。

- 分類と名前が**素材の行にある**ことが前提。実行記録の中にあると、別のTakeから引けない
- 同じバイト列が別スコープに重複している現状(`kato.jpg` が3行)は、**チェックサムで名寄せできる**はず。統合の可否は未決定(下記)
- 昇格の力学は既に正しい: trigger が widen-only を強制し、brand スコープへの書き込みは core 権限が要る(0028)。UIが無いだけ

## 15. 変えてはいけないもの

- **R2キーは内容アドレス**。名前は行が持つ。名前を変えてもバイトは動かない
- **原本を消さない**。トリミングも変換も派生として作る
- **決めつけて入れ、直せるようにする**。空欄で人に埋めさせるのは、このプロダクトの他の場所と矛盾する
- **画像の加工は取り込み時**。描画時のフィルタで形を変えない
- **レンダーは再解決しない**。基盤の注入は作成時の投影+pinであり、レンダー時に「現在のブランド素材」を引き直さない([data-model.md §4](data-model.md) の既存契約)
- **スコープは広がるだけ**。昇格しても id と R2 キーは変わらない(0028 の trigger が正本)
