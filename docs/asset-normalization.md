# 素材の正規化とインベントリ(仕様)

最終更新: 2026-08-16
ステータス: **仕様のみ・未実装**。この文書が「アップロードされた素材をどう整えるか」の正本

## 1. この文書が答える問い

> 雑に入れた素材が、**整理されて出てくる**にはどうすればよいか。

対象は、素材が入ってから成果物に使われるまで——アップロード/スクレーピング → 分類 → 命名 → 保存 → 再利用 → 書き出し。**成果物そのものの作り方は対象外**(動画は [deliverable-architecture.md](deliverable-architecture.md)、状態の見せ方は [video-state-model.md](video-state-model.md))。

## 2. なぜ動画より先に素材か

出力の品質は素材の品質で決まる。そして**編集可能性も素材で決まる**——余白だらけのロゴを受け取った動画は、どう組んでも余白だらけになる。いま作り込んでいるのは動画側だが、その一つ手前に手を入れないと、テンプレートの精度を上げるほど「素材が悪いせいで綺麗にならない」に突き当たる。

現実のワークフローの問題はここにある:

- サイトから拾ってきたロゴは**周囲の余白が大きい**
- 同じロゴに**版が多い**(黒・白・透過・横組み・シンボルのみ)
- どれが「その会社の正しいマーク」なのか、ファイルを見ても分からない

このツールを通せば素材が正規化される、という状態を作る。そうすると副産物として**素材のインベントリ**ができ、それ自体が資産になる。作るたびに素材が散らばるのではなく、作るたびに整っていく。

## 3. いま起きていること(2026-08-16 の実データ・47行)

推測ではなく `brand_materials` を数えた結果:

| 事実 | 数 | 意味 |
| --- | --- | --- |
| `label` がアップロード時のファイル名のまま | 全行 | `2.png`(2.4MBの写真)、`kato.jpg` のような名前が正本になっている |
| `width` / `height` が null | **47/47** | 列はあるが一度も埋めていない。解像度で名前を分けることが今はできない |
| `source_url` が null | **47/47** | スクレーピングで取った素材の出所が残っていない |
| `derived_from_material_id` を使っている行 | **0** | 派生を表す仕組みはあるが、作る側がいない |
| `logo_id` を持つロゴ | 5件中1件 | ロゴ正本エンティティと素材がほとんど繋がっていない |

さらに、同じ素材の版が既に散らばっている:

- `kato.jpg` / `miyao.jpg` / `onishi.jpg` が**それぞれ3行**。同じ名前で、work スコープに小さい版、take スコープに大きい版。どれが原本かは行を見ても分からない
- **`leopalace21` が `kind: logo`(PNG・work)と `kind: photo`(JPEG・take)の両方に存在する**。同じ会社の同じマークが、片方はロゴ、片方は写真として入っている

最後の1件は重要で、**README の既知バグ「ロゴが真っ白な板になる」と根が同じ**。JPEGとして入った leopalace21 が白抜き(`knockout`)されて全画素白く塗られた。「これはロゴである」「これは地の付いたラスタである」が素材側に無いから、毎回その場で判定するしかなく、判定を間違えると絵が壊れる。

分類そのものも、いまは**構造化LLMが実行のたびにその場で判定**し、`take_runs.steps` の実行記録にしか残らない。だから (1) 再実行のたびに再判定・再課金、(2) 素材一覧を分類で絞れない、(3) 別のTakeへ引き継げない。

## 4. 目指す体験

1. 雑に入れる。サイトのURLでも、Slackから落としたフォルダごとでも
2. **勝手に仕分けされる**。人物・製品・ロゴ・背景・資料。ロゴはさらに、黒/白/透過/どの主体のものか
3. **勝手に名前が付く**。中身が分かる名前に。解像度も名前に入る
4. 気に入らなければ**プルダウンで直せる**。分類は決めつけて入れるが、決定権は利用者にある
5. **そのままダウンロードできる**。整理された状態で
6. 書き出したプロジェクトの中も**同じ整理のまま**

「雑に入れたつもりが、綺麗になって出てくる」。これが体験の全部。

## 5. モデル: 2軸

**「素材が何であるか」と「この成果物で何として使うか」は別の問いなので、別に持つ。**

| 軸 | 問い | 例 | 誰のものか |
| --- | --- | --- | --- |
| **種別**(軸1) | この素材は何か | 人物 / 製品 / ロゴ / 背景 / 装飾 / 資料 | **素材の属性**。どの成果物から見ても同じ |
| **役割**(軸2) | この動画で何として使うか | キービジュアル / プログラムの地 / 登壇者の写真 / 提供マーク | **使用の属性**。成果物ごとに変わる |

分ける理由は、**キービジュアルが人物写真にも製品写真にもなり得る**から。割り当てはイベントのオントロジー次第で決まるので、素材側に焼き付けてはいけない。逆に「これは人物の写真だ」は成果物と無関係に真なので、毎回LLMに聞き直すのは無駄で、間違えると絵が壊れる。

- 軸1は `brand_materials` の列にする(**migration が要る**)。既存の `kind`(`photo` / `logo` / `audio` / `document` / `illustration`)は粗すぎるので、これを置き換えるか下位に分ける
- 軸2は使う側(`brief` のスロット、`take_inputs`)が持つ。**現状もそうなっている**ので変えない
- **語彙はテンプレート非依存にする**。いまの分類語は event-cm 専用(`speaker-portrait` / `venue` があり `product` が無い)。製品CMでも通じる語に作り直す
- **どちらも手で直せる**。分類は決めつけて入れる(空欄にしない)が、プルダウンで覆せる

## 6. ロゴが持つ下位属性

ロゴだけは追加で属性を持つ。ロゴは「1社に1ファイル」ではないため。

| 属性 | 値 | 測り方 |
| --- | --- | --- |
| **地の有無** | 透過 / 地あり | `measureArtwork()` が既に測っている(`opaque`) |
| **明度** | 暗いマーク / 明るいマーク | 同上(`luminance`) |
| **主体** | どの会社・事業・製品・イベントのものか | ロゴ正本エンティティ(`logo_id`)と繋ぐ |
| **解像度** | 幅×高さ、またはベクター | **`width`/`height` を埋める**(いま全行null) |
| **構成** | 横組み / 縦組み / シンボルのみ | 判定は後回しでよい。人が直せれば足りる |

測定は既にある([lib/event-cm/extract.ts](../lib/event-cm/extract.ts) の `measureArtwork`)。**足りないのは、測った結果を素材の行に残していないこと**だけ。

## 7. 名前が正本(ファイル名ドリブン)

**フォルダは便宜、名前は契約。** 極端に言えばフォルダが無くても、名前が長ければ用は足りる。名前だけで意味が通るなら、ZIPを解いた人も、grepする人も、AIエージェントも同じ理解にたどり着く。

命名の骨子(案):

```
assets/logo/wealthpark-lab_mark_transparent_dark_512w.png
assets/logo/leopalace21_wordmark_plate_light_800w.jpg
assets/person/miyao-yoshiaki_portrait_1600w.jpg
assets/keyvisual/sake-tasting_1920w.jpg
assets/document/flyer-2026-09-18.pdf
assets/audio/narration_ja_female-1.wav
```

- **`<主体>_<何か>_<属性>_<幅>.<拡張子>`**。属性は判っているものだけ入れる
- **幅を名前に入れる**。「大・中・小」はアップロード時点では決められないが、幅は測れば分かる。後から人が「これが大きい方」と判断できる
- ベクターは幅を持たないので `vector` と書く
- **拡張子を必ず付ける**。いま書き出しに拡張子の無いファイルが出ている(R2キーのbasenameがチェックサムのため)
- 日本語名は**付けない**。ZIPのファイル名表はUTF-8フラグを立てないので、`unzip` が展開を拒む([lib/export/naming.ts](../lib/export/naming.ts) に同じ理由の先例がある)

### 内容アドレスと人間可読名は両立させる

いまR2キーは**内容アドレス**(チェックサム)で、これは重複排除と不変性のために正しい。一方で人が読む名前は同じバイト列に対して**複数あり得る**(同じ写真が別の動画で別の役割を持つ)。

だから**R2キーは内容アドレスのまま変えない**。人間可読名は**行が持つ**(`label` を「表示名」として正規化する、または表示名の列を足す)。書き出し・ダウンロード・一覧が読むのは行の名前で、保存の同一性はチェックサムが握る。**名前を変えてもバイトは動かない**、が守るべき性質。

## 8. 書き出しに同じ整理が出る

[プロジェクト書き出し](../README.md#プロジェクトデータの書き出しロックインしない)が吐く `public/materials/<uuid>/<checksum>` は、いま**第三者にとって読めない**。正規化後は:

```
public/assets/logo/wealthpark-lab_mark_transparent_dark_512w.svg
public/assets/person/miyao-yoshiaki_portrait_1600w.jpg
```

`props.json` の参照もこのパスになる。**整理された状態のまま持ち出せることが、正規化の意味の半分**——手元で続きを作る人が、どのファイルが何かを名前だけで判断できる。

## 9. 余白のトリミング(相談事項)

サイトから拾ったロゴは余白が過大なことが多く、そのまま組むと**版面の設計が効かない**(実際 event-cm のマークは `scale` で個別に逃がしている)。

- **画像の加工は取り込み時に行う。描画時のフィルタではやらない。** これは既に確立した原則で、「フィルタは板を切り抜けない——マークの上に塗るだけ」という失敗から来ている(commit `1c95bdf`)。トリミングも同じ側に置く
- **決定論でできることはLLMに聞かない**。余白の除去は α または輝度の境界を走査すれば求まる。`sharp` は既に使っていて、[labs/event/scripts/prepare-assets.mjs](../labs/event/scripts/prepare-assets.mjs) に前例がある
- **LLMが要るのは判断が要るところだけ**: 「この余白はデザインの一部か、切り落としてよい余白か」「この画像に写っているのはロゴか、ロゴが写り込んだ写真か」
- **原本は消さない**。トリミング結果は**派生素材**として作る。`derived_from_material_id` 列が既にあり、使う側がいない——ここが最初の使い手になる。切りすぎたときに戻れることが、自動でトリミングしてよい条件

## 10. インベントリとしての再利用

素材はいま3スコープを持つ(`take` / `work` / `brand`)。正規化された素材は**上のスコープに昇格するほど価値が出る**——同じロゴを次の動画でも、LPでも使える。

- 分類と名前が**素材の行にある**ことが前提。実行記録の中にあると、別のTakeから引けない
- 同じバイト列が別スコープに重複している現状(`kato.jpg` が3行)は、**チェックサムで名寄せできる**はず。統合の可否は未決定(下記)
- 将来、サイトをスクレーピングして素材を集め、LPと動画を作り、**綺麗になった素材だけを持ち出して自分でコーディングする**、という道筋がここで繋がる

## 11. 未決定事項

1. **軸1の語彙**。`person / product / logo / background / decoration / document` で足りるか。既存の `kind` を置き換えるか、下位に足すか
2. **同一バイトの名寄せ**。チェックサムが同じ行を統合するか、スコープごとに別行のまま残すか。統合すると「この動画に固定された素材」の意味が変わる
3. **命名を誰が決めるか**。決定論(主体名+測定値)でどこまで行けるか、意味のある短い名前(`sake-tasting`)にLLMが要るか
4. **リネームの遡及**。既存47行を移行するか、これから入るものだけ正規化するか
5. **トリミングの既定**。自動で切るか、提案して人が承認するか
6. **UIの置き場所**。素材一覧はどの画面に立つか(いまパイプラインのドロワーの中にしかない)

## 12. 段階(案)

1. **測って残す**。`width` / `height` / `opaque` / `luminance` / `source_url` を取り込み時に埋める。**migration のみ・見た目は変わらない**。これだけで白板バグの再発条件が消える
2. **軸1を列にする**。語彙を決め、構造化LLMの判定結果を素材の行へ書く。プルダウンで直せるようにする
3. **名前を正規化する**。表示名を作り、書き出しがそれを使う
4. **派生とトリミング**。`derived_from_material_id` に最初の使い手を作る

各段でテストを green に保つ。1と2の間で語彙が変わるので、**1を先に入れても2の判断を縛らない**のが順序の理由。

## 13. 変えてはいけないもの

- **R2キーは内容アドレス**。名前は行が持つ。名前を変えてもバイトは動かない
- **原本を消さない**。トリミングも変換も派生として作る
- **決めつけて入れ、直せるようにする**。空欄で人に埋めさせるのは、このプロダクトの他の場所と矛盾する
- **画像の加工は取り込み時**。描画時のフィルタで形を変えない
