# 動画編集の状態モデル(編集・映像・出力の3層と未反映差分)

最終更新: 2026-08-15
ステータス: **§6 の1〜4段目を実装済み**(差分のフィールド化・サーバー1箇所への集約・表示面・オールグリーン)。残るのは絵コンテのコマの点とFactListのチップ。この文書が「編集中・未反映・オールグリーン」の体験の正本

## 1. この文書の範囲

動画詳細画面(`/brands/[id]/video/[videoId]`)における**状態の見せ方**の仕様。答える問いは1つ:

> 「いま編集した内容は、どこまで動画に反映されているのか」を、ユーザーが**どの画面部品を見ても同じ答えで**分かるようにするにはどうするか。

きっかけになった事象: BGMを差し替えて「使用中」になったのに、プレイヤーの音楽は変わらず、**「動画を作り直す」の差分も0件のまま**だった。仕様(焼き付けるまで変わらない)は正しく動いていたが、**画面がそれを言っていなかった**。

前提となるリファクタリング(brief / baked_brief の分離、`eventCmFilm()` への一本化)は完了済み。経緯は [old/event-cm-refactor-plan.md](old/event-cm-refactor-plan.md)(アーカイブ)。本書はその上に立つ**仕様**であり、リファクタリングの記録は含まない。

## 2. モデル: 3層の鎖

この画面の実体は「編集モード/プレビューモード」の切り替えではなく、**3層のデプロイの鎖**である。データとしては既に存在している——名前と可視性が無かっただけ。

```
編集(brief) ──未反映N件──▶ 動画(baked_brief) ──古いMP4──▶ 出力・公開(MP4 / URL)
 絵コンテ・項目一覧・各ドロワー   プレイヤーが再生する版        書き出し・/v/[id]
 = ステージング                = デプロイ済み              = 配布物
```

- **境界1(編集→動画)**: 「動画を作り直す」だけが越える。差分の答えの正本は [../lib/event-cm/bake.ts](../lib/event-cm/bake.ts)(本仕様で拡張する)
- **境界2(動画→MP4)**: 書き出しだけが越える。既存の `renderIsBehind` が答える(「このMP4は、いま再生されている動画より古いバージョンです」)

**モード切替は作らない**。画面は常に作業場、プレイヤーだけが常に成果。モードを切り替える設計は「いまどちらを見ているのか」という新しい混乱を生む。代わりにプレイヤーが**自分の版を名乗る**(§5)。

## 3. 決定事項

### 3.1 「未反映」は正常な状態。だから赤にしない

この画面では**差分があるのが常態**である(編集すれば必ず差分が生まれる)。常態を赤で塗ると、赤が常時点灯のランプになり、本当の失敗と見分けがつかなくなる。「何も壊れていないのに警告が出る状態は、警告を無視する習慣を作る」([../lib/event-cm/facts.ts](../lib/event-cm/facts.ts) が既に持つ原則)。

**色の意味論を3色で固定する**:

| 色 | 意味 | 使う場所 |
| --- | --- | --- |
| **琥珀(amber)** | 未反映。正常な作業中の状態 | 差分バッジ・コマの隅の点・プレイヤーの注記・「未反映」チップ |
| **緑** | 一致。編集=動画=(あれば)MP4 | オールグリーン表示「最新の状態です」 |
| **赤** | 失敗だけ | レンダー失敗・保存エラー・読み上げ上限超過(既存) |

琥珀はシナリオ字数の「目安超過」で既に使っている色。語彙の追加ではなく統一。

### 3.2 差分はフィールド単位。保存形ブリーフ同士を比べる

現行の `bakeState` は3つの刻印(`factsUpdatedAt` / `scenario.updatedAt` / `voice.track.generatedAt`)しか比べないため、「**何が**未反映か」を言えない。さらに `factsUpdatedAt` は `isSpokenFact` が BGM・写真・ロゴを意図的に除外しているので、**読み上げないが映像には出るもの**が構造上ぜったいに差分にならない(BGM差し替えが0件だった直接の原因)。

これを**保存形ブリーフのフィールド単位の突き合わせ**に変える:

- 比較は **DBに保存されている形**(`material:<uuid>` ポインタ)同士で行う。署名URLは保存形に存在しないので、「deep equal はしない(URLが毎回変わるから)」という従来の制約は**理由ごと消える**
- 比較の語彙は `EVENT_CM_GOAL` の path をそのまま使う。ラベル(「BGM」「主役の写真」「開催日」)が既にあり、**直す場所と同じ語で未反映を言える**
- suppression の差(消した/戻した)も、そのフィールドの変更として数える
- `scenario` はシーンのテキスト列で、`voice` は `track.generatedAt` で比べる(録音の同一性は従来どおりポインタではなく刻印)

### 3.3 計算はサーバー1箇所。クライアントは描くだけ

現行は同じ `bakeState` がサーバー(生ブリーフ)とクライアント(署名URL解決後のブリーフ)の**2箇所で、違う形のデータに対して**走っている。この構図自体が次のバグの置き場所(BGMピッカーが選択を表示できなかった過去のバグと同じ形)。

- 差分の計算は [../lib/event-cm/bake.ts](../lib/event-cm/bake.ts) に置いたまま、**呼ぶのはAPIルートだけ**にする
- take GET と pipeline GET が同じ関数の答えを**マニフェスト**(§4)として返し、クライアントの全表示面はそれを言い換える
- `eventCmFilm()` と同じ規律: **1箇所で導出し、消費者は導出しない**

### 3.4 `factsUpdatedAt` は元の1つの仕事へ戻す

`factsUpdatedAt` は「**シナリオが古いか**」(`scenarioStaleness`)だけを答える刻印に戻る。bake の差分判定には使わない。1つの値に2つの問いを答えさせたことが、除外リスト(`isSpokenFact`)をそのまま差分の盲点にした。

### 3.5 差分の種類が、必要な工程を決める

「BGMを変えたら読み上げは要らない」を機械的に導く。各差分に `needs`(この差分を反映するのに必要な工程)を付ける:

- **読み上げる事実**(`isSpokenFact` が真: タイトル・日程・登壇者・プログラム等)の差分 → `needs: ["scenario", "voice", "bake"]`(シナリオが古くなる→読み直しが要る→反映)。ただし `scenario.source === "human"` なら `scenario` は入れない(手書きは上書きしない・既存規則)
- **見せる/鳴らすだけのもの**(BGM・写真・ロゴ)の差分 → `needs: ["bake"]`
- `scenario` 自体の差分 → `needs: ["voice", "bake"]`(読み上げオフなら `["bake"]`)
- `voice` の差分 → `needs: ["bake"]`

「動画を作り直す」が実際に通す工程は全差分の `needs` の合成。**BGMだけ変えたときは反映のみが走り、数秒で終わる**(TTS課金もLLM呼び出しも走らない)。`pendingFilmSteps` の既存の2つの拒否(手書きシナリオ・読み上げオフ)はそのまま生きる。

## 4. データ契約: 差分マニフェスト

take GET(`/api/brands/[id]/videos/[videoId]`)と pipeline GET が同じ形で返す。**クライアントはこれを計算しない**。

**実装済み**([lib/event-cm/bake.ts](../lib/event-cm/bake.ts) の `FilmPending` / `filmPending()`):

```ts
pending: {
  /** プレイヤーが再生している版の時刻。null = 一度も実行していない(案内表示・琥珀ではない) */
  bakedAt: string | null;
  /** 境界1の差分。保存形ブリーフのフィールド単位比較。空 = 編集と動画が一致 */
  changes: Array<{
    path: string;          // EVENT_CM_GOAL の path("bgm" / "visuals.value" / "guests[0].photo" …)
    label: string;         // 同 goal のラベル(「BGM」「主役の写真」…)。画面はこれをそのまま言う
    needs: FilmStep[];     // この差分の反映に必要な工程(§3.5)
  }>;
  /** 「動画を作り直す」が実際に通す工程(changes.needs + 作業中ブリーフ自身の未了分の合成) */
  steps: FilmStep[];
  /** 未処理ゼロで押されたときに通す工程。ボタンはゼロでも押せるので、その press が
   *  何をするかをブラウザに計算させないために一緒に配る */
  redoSteps: FilmStep[];
}
```

- **`unread`(資料の未読件数)はマニフェストに入れない**。`FilmStep` は `scenario / voice / bake` の3つで、読み取り3段は別の語彙だから。ボタンのバッジは従来どおり `pendingStages.length + steps.length` で合成する——読み取り段の判定([lib/pipeline/stage-actions.ts](../lib/pipeline/stage-actions.ts))は署名URLの影響を受けないので、クライアントで導出しても壊れない
- どのテンプレートがこのマニフェストを持つかは**台帳が宣言する**([lib/templates/catalog.ts](../lib/templates/catalog.ts) の `bakesBrief`)。APIルートに `template_id === "event-cm"` を書かない
- 境界2(MP4の古さ)は従来どおり `renderIsBehind` で別に運ぶ。MP4は鎖の外(§9.4の決定は不変)なのでマニフェストに混ぜない。オールグリーン判定(§5)だけが両方を見る
- 件数の畳み方: `describeChanges()` が**頭3件+「他N件」**で畳む。構造化が一度に12項目書き換えても帯が画面を覆わない

## 5. 表示面の仕様(6つの面、1つの答え)

すべて §4 のマニフェストの言い換え。**どの面も自分で差分を数えない。**

| 面 | 仕様 |
| --- | --- |
| **プレイヤー** | 版を名乗り、状態を1語で持つ(`filmStatus()`。**4状態**): `unrun`=案内(「下書きのままの再生です」・琥珀ではない)/ `behind`=琥珀の細枠+「再生中は8/15 14:03の動画です。そのあとの変更が3件あります(BGM、主役の写真、シナリオ)」/ `matched`=絵コンテとは一致しているが工程が残る(グレーで残り工程を言う)/ `settled`=緑。**`matched` を緑にしてはいけない**——実データで、差分ゼロなのにボタンが「未処理3件」を出すTakeがあり、緑の直上に矛盾が出た |
| **「動画を作り直す」ボタン** | 琥珀バッジに `changes.length + unread`。ラベル/ツールチップは `steps` から作る(「読み上げる・動画に反映する」)——残り1工程のときに嘘をつかない(既存の stage-actions と同じ規則)。差分ゼロでも押せる(全部もう一度・既存仕様) |
| **ヘッダーのボタン(BGM・読み上げ)** | 横のドットが**3状態**([components/video/StatusDot.tsx](../components/video/StatusDot.tsx)): 緑=オンで反映済み / **琥珀=変えたがまだ反映していない** / グレー=オフ。以前は在/不在だけを言っていたので、曲を変えた直後も緑のままで「済んだ」に読めた。**変更した本人がその場で見る面**なので、ここが最初に色を変える |
| **項目一覧(FactList)** | `changes` に居る行へ琥珀の「**未反映**」チップ(由来チップの隣)。直す場所と未反映を言う場所を分けない |
| **絵コンテのコマ** | 未反映フィールドを映しているコマの隅に琥珀の点。コマ→フィールドの対応は `SceneComponent.fields`(既存)から導出。シナリオ1行の差分はそのコマだけに点が付く |
| **パイプラインバー** | 資料投入→入力段に「未読N件」(`unread`)、事実・シナリオ・読み上げの差分→映像段(4段目)に件数。給源をマニフェストへ差し替えるだけで、バッジ機構は既存 |
| **オールグリーン** | `changes` 空 && `bakedAt` あり && (MP4が無い or `renderIsBehind` が偽) のとき、プレイヤー横に静かな緑で「**最新の状態です**」。**無警告と安心は別物**なので、ゴール状態は明示的に言う |

文言の原則(既存の製品原則の適用):

- 未反映は**名前で言う**(「変更があります」ではなく「BGM、主役の写真」)
- 何が起きるかは**工程で言う**(「実行してください」ではなく「読み上げる・動画に反映する」)
- 消えた/古い/未実行を混同しない(未実行=案内、未反映=琥珀、失敗=赤)

## 6. 実装計画(4段・各段でテストgreenを保つ)

1. ✅ **マニフェスト**(2026-08-15): `bakeChanges()` がフィールド単位で比較し、`BakeChange` は `{path, label, needs}`。`pendingFilmSteps` は差分の `needs` と作業中ブリーフ自身の未了分の合成。`factsUpdatedAt` は差分判定から外れ、シナリオの陳腐化だけを答える
2. ✅ **API**(2026-08-15): take GET が `pending` を返し、pipeline GET は同じ `bakeChanges()` を読む。**クライアントの `bakeState` / `pendingFilmSteps` 呼び出しは撤去**——ブラウザは差分を計算しない。1段目と2段目は分けられない(フィールド比較にした瞬間、署名URLを持つクライアント側計算は必ず誤差分を出すため)
3. ✅ **表示面**(2026-08-15): プレイヤーの版名乗り+琥珀のリング、ヘッダーのドットの3状態化(`StatusDot`)、BGMダイアログの未反映表示。**残り**: FactListの「未反映」チップと絵コンテのコマの点
4. ✅ **オールグリーン**(2026-08-15): `filmStatus()` が4状態を1語で答え、`settled` のときだけ緑。**`matched`(絵コンテとは一致だが工程が残る)を緑にしない**のが要点

**受入条件**:

- BGMを差し替える → プレイヤー直下に「未反映の変更 1件 — BGM」、ボタンに琥珀バッジ1、押すと**反映だけ**が走って数秒で一致し、緑「最新の状態です」が出る
- シナリオを1行直す → そのコマに琥珀の点、差分は「シナリオ」、工程は「読み上げる・動画に反映する」
- 資料を投入する → 入力段に「未読1件」、ボタンのバッジが増える
- 署名URLの再発行(ページ再読込)では差分が**出ない**
- 未実行のTakeは琥珀を1つも出さず、従来どおり案内だけ

## 7. 変えてはいけないもの(この仕様が上書きしない契約)

- **映像の唯一の導出は `eventCmFilm()`**。マニフェストは「何が違うか」を言うだけで、映像を導出しない
- **MP4は鎖の外**。「動画を作り直す」にMP4を含めない(§9.4)。境界2は `renderIsBehind` のまま
- **手書きシナリオ(`source: "human"`)は自動で書き直さない**。差分には出す(未反映は事実)が、`needs` に `scenario` を入れない
- **読み上げオフは suppression**。オフ中は `needs` に `voice` を入れない
- **未実行は案内であって警告ではない**。「追加した瞬間に完成した映像が再生される」体験を琥珀で汚さない
- 差分の答えは **`bake.ts` 1箇所**(場所は変えず、粒度と呼び出し元だけが変わる)
