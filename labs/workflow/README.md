# Workflow Lab — ブランドビジュアル生成パイプライン(保証モード・基盤要件書)

ロゴプラットフォームの中核となる「モックアップ/ブランドビジュアル生成パイプライン」の研究所。実験場は `/labs/workflow`。

この文書は**保証モードの開発要件の正本**(事業側の基盤要件書 2026-07 を反映)と**実装状況**を兼ねる。技術選定はディープリサーチ(2026年7月実施)と事業側の議論に基づき**決定済み**。選定の再検討が必要になった場合は実装前に相談すること。

> **位置づけ(2026-07-12 のラボ再編)**: このラボの旧称は Image Lab。ラボ群を「保証モード(ロゴに触れない)/探索モード(生成AIがロゴを解釈する)」の二層に再編した際、決定論的合成とプロツール連携(Photoshop・Figma・ヘッドレスBlender)を担う**保証モードのワークフロー実験場**として改称した(旧URL `/labs/image` はリダイレクト)。対になる**探索モード**の要件は続編の [Generative Lab README](../generative/README.md) が正本。モード分類の考え方は [labs/README.md](../README.md) を参照。

## 設計の大原則(全実装判断の基準)

**「舞台はAIで生成し、ロゴは決定論的に合成する」。生成モデルにロゴ本体を絶対に触れさせない。**

理由: 現行の画像生成・編集モデルは「ロゴをなるべく保つ」ことはできても「絶対に不変」は保証しない(各社とも契約・ドキュメント上ピクセル固定を保証していない)。当プロダクトの価値は「顧客のロゴを1ピクセルも崩さないこと」なので、ロゴはレイヤー合成・テンプレート差し替えという決定論的処理でのみ扱う。AIの役割は「ロゴが載る舞台(シーン)」の生成に限定する。

この原則から導かれる推論: **迷ったら「ロゴに触れない側」の実装を選ぶこと。**

### 第2原則(2026-07-14追加): 重いプロツールはテンプレート制作時にだけ走らせる

**Blender・Photoshop・Figma 等のプロツールを使うのは運営側のテンプレート制作パイプライン(オフライン)のみ。ユーザーのオーダー時に走るのは常に Phase 1 の決定論的合成エンジンだけ**(変動費ゼロを維持)。

- テンプレートを制作するのは運営側のみ。ユーザーはカタログからの**選択とカスタマイズ**(例: プレゼンのマグカップをステッカーに差し替える)だけを行い、テンプレート制作ツールには触れない。テンプレート制作を不特定多数に開放する計画はない
- プロツールの成果物はすべて `logos-2d-template@1` に**焼き込む**。ランタイムに新しいインフラ(レンダーワーカー等)を持ち込まない
- オーダーごとのランタイムレンダリングは、焼き込みでは実現できない出力(ターンテーブル動画等)が必要になった時に初めて検討する(導入候補リスト参照)

## アーキテクチャ: 5層構成

### Layer 1: テンプレート層(内製・差別化の本丸)

デザイナー品質の「舞台テンプレート」ライブラリ。

- **2Dテンプレート**: 合成に必要なメタデータを持つ自前フォーマット `logos-2d-template@1` を定義済み。合成面の四隅座標(パース)、ディスプレイスメントマップ(布のシワ・面の凹凸)、ライティング/シャドウの乗算レイヤー、ブレンドモード指定、ロゴの推奨配置とクリアスペースを持つ。さらに **`presentation.allowedPlacements` / `presentation.defaultMappings`** を持ち、「どの presentation placement に差し込めるか」「初期状態でどこに採用するか」を定義する。旧 `presentationScene` / `presentationAdopted` / `presentationOrder` は後方互換として残す。PSDのスマートオブジェクト方式の自前フォーマット再現。仕様の正本は [core/template-format.ts](core/template-format.ts)(型定義+バリデーション)
- **3Dテンプレート(Blender焼き込み)**: Blenderシーンファイルを制作時の**原盤**とし、レンダーパス一式(背景ビューティ・ライティング/シャドウ乗算レイヤー・UVワープマップ・ロゴ配置ジオメトリ)をヘッドレスCLIで書き出して `logos-2d-template@1` へ**焼き込む**(Phase 2)。ランタイムにBlenderは不要(第2原則)。`.blend` は原盤として保管し、カメラ・ライティング違いの派生テンプレートを同一シーンから量産できるようにする
- テンプレートの中身(デザイン)はデザイナー側で制作する。エンジニアリング側の責務は**フォーマット定義・バリデーション・追加が容易なパイプライン**。**テンプレート追加にコード変更が不要な状態**が実装済みのゴール: [templates/](templates/) にディレクトリ(`template.json`+アセット)を置くだけでカタログに現れ、不正なテンプレートはバリデーションエラーとしてUIに表示される

### Layer 2: 合成エンジン層(内製)

- 2D合成: **sharp** を基本とし、パース変換(ホモグラフィ)とディスプレイスメントは外部バイナリ依存を避けて純TypeScriptで実装([engine/](engine/))。処理内容: SVG/PNGロゴのラスタライズ(出力解像度に応じた適切なサイズ・2倍スーパーサンプル)、ホモグラフィ射影、ディスプレイスメント適用、ライティング乗算、シャドウ合成
- 曲面合成: 四隅ホモグラフィでは表現できない曲面(マグの円筒面・ボトル・キャップ等)のために、**UVワープマップ**(ピクセル単位のUV参照マップ。BlenderのUVパスから焼き出す)による合成モードをエンジンに追加する(Phase 2)。純TS実装の方針は維持
- ランタイム3Dレンダリング(ヘッドレスBlenderワーカー)は将来枠(第2原則・導入候補リスト参照)。導入する場合はレンダリング時間とインフラコストを計測できるようにする(コスト管理はプロダクト要件)
- 出力: 標準2K相当。**解像度はパラメータ化済み**(`width` 指定、印刷用高解像度は将来要件)

### Layer 3: 舞台生成層(外部API・抽象化必須)— Phase 3

ユーザーが独自シーンを要求したとき(課金機能)のみAI生成を使う。

> **再編後の注記**: プロバイダ抽象化レイヤーは探索モード([Generative Lab](../generative/README.md) の3エンジン構成)と**共有する基盤**になる。実装時は両モードからの利用を前提に設計すること。本ラボ(保証モード)での用途は「ロゴが載る舞台の生成」に限定され、ロゴ本体は引き続き Layer 2 で決定論的に合成する。

- **プロバイダ抽象化レイヤーを必ず設ける**(モデル世代交代・エンタープライズ要件での切り替えに備える)
- 第一プロバイダ: **Recraft V4.1**(標準ラスタ、$0.035/枚)。低コスト、API入出力を学習に使わない明文規定、ベクター対応
  - **必須要件**: Recraftの生成物は約24時間、署名付きURLで公開アクセス可能な状態で残る。**生成完了後ただちに自前ストレージへ転送し、以後は自前URLのみを参照する**(顧客の未公開ロゴを扱う前提)
- 構造制御が必要な場合: **Together経由のFLUX系**(ZDRデフォルト、学習利用opt-inでデフォルトoff)
- 将来のエンタープライズ向け: **Vertex AI経由のGemini画像モデル**(IP補償対象)。抽象化レイヤーはこの切り替えを見越す
- **使用禁止**:
  - Black Forest Labs 直API(入力・出力をモデル学習等に利用できる規約。FLUXは必ずTogether等のZDR基盤経由)
  - Ideogram API(「Powered by Ideogram」表示義務がホワイトラベル要件と衝突)
- OpenAI画像APIは、IP補償から商標の商用利用起因クレームが除外されているため優先度低。使う場合は事業側に確認

### Layer 4: QAゲート層(内製・これ自体が製品価値)— Phase 2

生成・合成結果がブランド準拠かをルールベースで自動判定するゲート。「デザインハーネスエンジニアリング」の実体であり、検証ルールの蓄積が資産になる。

> **再編後の注記**: スコアリング基盤は探索モードの**逸脱スコアボード**([Generative Lab](../generative/README.md) E-4)と共有する。同じ忠実度スコアが、保証モードでは内部回帰テスト、探索モードではユーザーに提示する計器盤(「この生成物のロゴ忠実度: 94%」)として使われる。

初期実装の対象:
- ロゴ領域の忠実度検証: 合成後画像からロゴ領域を切り出し、元ロゴと構造比較(エッジ比較、パーセプチュアルハッシュ、色差ΔE)。決定論的合成では本来劣化しないはずなので、主にパイプライン自体の回帰テストとして機能
- 配置ジオメトリ検証: クリアスペース侵犯、最小サイズ割れ、テンプレート規定位置からの逸脱の検出(※Phase 1では配置計算側で常に守る実装になっている)
- 舞台生成物の検証: 意図しない文字・ロゴ様図形・不適切要素の検出(OCR+分類)
- 判定結果はスコアとフラグで記録し、閾値未満は自動リトライまたは人間レビューへ。閾値は設定可能に

### Layer 5: 仕上げ層 — Phase 4

- アップスケール: Recraft crisp upscale($0.004)第一候補、品質不足ならTopaz API。インターフェースだけ先に切る
- ライティング調和: 当面は**テンプレート側に焼き込んだライティングで対応**し、自動調和(Firefly Object Composite等)は導入しない(未解決事項1参照)

## 横断要件

### データ取り扱い(契約上の生命線)

- 顧客のロゴおよび生成物を外部APIに送信する場合、**保持ポリシーと学習利用条項が確認済みのプロバイダのみ**(上記の許可リスト方式)。新プロバイダ追加時は必ず事業側の確認を通す
- 外部API上に残るデータは最小化: 生成物は即時回収、fal等は保持opt-outヘッダ必須
- どの顧客データがいつどの外部APIに送られたかの監査ログを残す

### コスト計測(初期からの必須要件)

- 1生成ジョブごとに、外部APIコスト・レンダリング時間・リトライ回数を記録し、**ユーザー単位/テンプレート単位の原価を集計できる**ようにする。価格設計とCAC計算の基礎データ
- 実装: [engine/job-log.ts](engine/job-log.ts) が全ジョブを `var/workflow-lab/jobs.jsonl`(gitignore済み)にJSONLで記録。`/api/labs/workflow/jobs` がテンプレート単位の集計を返し、実験場のフッターに常時表示される

### コンテンツフィルタ対策

- 本設計ではロゴを生成APIに送らないため通常フローでは発生しない想定。舞台生成プロンプトに社名等を含める場合(Phase 3)はフィルタ起因エラーを識別してハンドリングし、発生率をログする

## 導入候補リスト(未フェーズ化のアイデア置き場・2026-07-14)

フェーズには載せないが破棄もしないアイデア。着手を決めたらフェーズ表へ昇格させる。いずれも第2原則(重いツールは制作時のみ)に従う。

- **実写キャリブレーション**: マーカー(チェッカーボード/ArUco)を貼った実物を撮影し、四隅・パース・シワマップを抽出して**実写テンプレート**化する運営側ツール。簡易版は「写真アップ→四隅ドラッグの手動アノテーションUI」でPhase 1エンジンのまま成立する。将来的には「導入企業の実店舗・実製品にロゴが入る」という、生成AIには原理的に出せない(実在保証がない)価値に接続できる
- **Figmaインジェスト**: 命名規約付きFigmaファイルからAPI経由で平面系テンプレート(名刺・OGP・スライド・サイネージ等)を自動生成する制作効率化ツール
- **PSDインジェスト**: スマートオブジェクト付きPSDを `template.json` に変換(スマートオブジェクトの変形行列=四隅座標、乗算レイヤー=ライティングレイヤーと概念が対応)。市販モックアップ資産の活用はライセンス確認が前提
- **人間ワーカー工程**: 合成ジョブに人間の作業ステップ(Photoshopでの最終レタッチ等)を挟み、成果物をQAゲート(Layer 4)でロゴ忠実度検証して採用する。「保証モード=決定論のみ」ではなく**「保証モード=出力のロゴ不変が検証されるもの」**への拡張
- **ランタイムBlenderワーカー**: オーダーごとの3Dレンダリング。焼き込みでは原理的に不可能な表現(ロゴ自体の立体化=エンボス/刻印/立体切り文字、ロゴ色に反応するライティング、任意アングル・ターンテーブル動画)に**圧倒的な差別化があるなら積極的に検討する**(2026-07-15ユーザー方針)。同期レスポンスは求めず、**有料会員向けのキュー+バッチ処理(数日待ちの「仕上がり品」)**のような提供形態も含めて柔軟に設計する。ラボは探索の場であり「焼き込みで済むから不要」と早期に切らない

  **✅ 第1スパイク: ネオンサイン**(2026-07-15初版 / 2026-07-16 確定版・[scripts/blender/neon_sign.py](scripts/blender/neon_sign.py))。任意のSVGロゴを取り込み、**各シェイプの輪郭を発光管化**して**ニュートラルな無地壁**の手前に灯す。管の色がグローバルイルミネーションで壁ににじむ。焼き込み不可能な理由の実証: ①**ロゴの形が3Dジオメトリになる**(平らなロゴを面に貼るのではない)②**ロゴがシーンのライティングになる**(壁への色にじみ)。しかも**生成AIを一切使わない**(SVG→カーブ→輪郭抽出→発光管→Cycles は全て決定論)ので、フォトリアルなのに**ロゴ不変が保証される**——Geminiにはできず焼き込みには届かない、保証モードのプレミアム階層。マーク単体もワードマーク(XTRUST・NEXT.js等)も無人で通ることを確認済み。per-order レンダー(分単位)=キュー/バッチ枠の想定。

  - **再現にMCP/GUIは不要**: Blender MCP はチューニング時の「目と手」(作業台)にすぎない。確定したレシピはスクリプトに焼き込み済みで、他ロゴでの再現は `Blender -b -P neon_sign.py -- --svg 別ロゴ.svg --out out.png` を回すだけ(決定論ゆえ差し替えても同じ質感)。
  - **確定版レシピ(2026-07-16・XTRUSTで詰めた美的方向)**:
    - **壁**: 煉瓦(チープだった)を廃し、ニュートラルな無地壁へ。**アルベドは均一**にし、複雑さは**細かい自然な法線bump(中スケール+微細グレイン)**だけで出す。「雲状の色ムラ(=大スケールのアルベドノイズ)」は不可——欲しいのは"見えなくてよい微かな陰影の揺らぎ"で、均一さを崩してフォトリアルに寄せるためのもの。
    - **フォグ**: 薄い**箱型ボリューム**(camera を内包する cube)。**WORLD に直付けするVolume Scatterは厳禁**——無限に広がる媒質になり、HDRI(無限遠)からの光が surface に届く前に消える。近接するネオンだけが効いて壁が真っ黒になる。フォグは必ず bounded box で。
    - **ワールド**: Poly Haven の屋内HDRI(`empty_warehouse_01`, CC0)を**低強度(0.22)**で。機械的な単調さに"空気の揺らぎ"を与える。CLIが `var/workflow-lab/hdri/` へ自動DL(`--hdri` で差し替え可)。
    - **カメラ**: 50mm・**f/0.1**(非現実的だが、このレンズ/絞りで見え方が一変するのが要点。背景がスムースに溶ける)。正面やや下からの仰ぎ。**フレーミングは実測バウンディングボックスから自動計算**するのでロゴ比率が変わっても破綻しない。壁はサインの背後(gap 0.35m)——近すぎると浮遊感が消える代わりにボケが弱まる。
    - **管/グロー**: 管半径は初版の80%に(細く)。emission 6.5(壁を照らす主光源も兼ねる)。Fog Glow は threshold 0 / size 6 で気前よく。
  - 技術メモ: SVGの塗りシェイプは**メッシュ化→境界エッジのみ残す→カーブに戻してベベル**で「塗り円盤」ではなく「発光リング」になる(単にカーブをベベルすると塗り面が残る)。露出は Filmic Medium High Contrast。**視覚判定は数値で**——壁が暗すぎ/明るすぎは目視で迷ったら露出を測る。
  - 次の候補: エンボス/箔押し革(SVG押し出し+ベベル+光沢)、キューUI(job投入→数日→仕上がり通知)、動画(ターンテーブル/管の点滅)。

## 未解決事項(実装前にプロトタイプで検証)

1. **ライティング調和の品質**: テンプレートに焼き込んだ光とAI生成した舞台の光の整合がどこまで自然か。Phase 3の前に小さな検証(数パターンの舞台×合成)を行い、事業側とレビュー
2. **fill-only SVGロゴのラスタライズ品質**: 細線・グラデーション含みロゴでの合成品質。テストロゴセットを用意して回帰テストに組み込む(Phase 2のQAゲートと合流)
3. **Blenderヘッドレスレンダーの制作コスト**: 実測済み(2026-07-14)——レンダー約3分/テンプレート(M系CPU)。オーダー時変動費ゼロは確認済み。量産時はGPU(Metal)有効化で短縮余地あり
4. **UVワープマップ合成の品質**: 一次検証済み(2026-07-14、1600pxテストロゴ目視)。エッジはプリマルチプライドUV+カバレッジ1%閾値で処理し目立つ破綻なし。細線ロゴ・高解像度出力での回帰はQAゲート(Phase 2.5)で体系化する
5. **mug-ceramic のリム左上に微小なシェーディングノッチ**: スピン生成メッシュのシーム起因の疑い。実用上目立たないが、シーン磨き込み時に解消する

### Blender焼き込みパイプライン(Phase 2 の使い方)

スクリプトは [scripts/blender/](scripts/blender/)。Blender はローカルの `/Applications/Blender.app` をヘッドレスで使う(4.x系。ランタイムには不要)。

```bash
# 1. 原盤シーンを生成(手続き的=再現可能。.blend は gitignore 済みの var/ に置く)
/Applications/Blender.app/Contents/MacOS/Blender -b \
  -P labs/workflow/scripts/blender/make_mug_scene.py -- \
  --out var/workflow-lab/scenes/mug-ceramic.blend

# 2. 焼き出し(3パスレンダー → テンプレートディレクトリ一式を生成)
/Applications/Blender.app/Contents/MacOS/Blender -b var/workflow-lab/scenes/mug-ceramic.blend \
  -P labs/workflow/scripts/blender/bake_template.py -- \
  --out labs/workflow/templates/mug-ceramic --id mug-ceramic
```

**シーン規約**(bake_template.py が要求): 印刷面は `PrintSurface` という名前のメッシュ(実面から0.4mm浮かせたデカールシェル)で、UVを0..1に張り、カスタムプロパティ `logos_print_aspect`(印刷面の物理的な幅/高さ)を持つ。それ以外のオブジェクトはすべて舞台として扱われる。オプションで **`PrintLight` という名前のマテリアル**をシーンに置くと、light パスの白ディフューズの代わりに使われる——布の織り目バンプ等を持つ白マテリアルにすれば、**印刷されたロゴがその素材の質感(織り目の陰影)を継承する**(tote-canvas で使用)。スタジオ(cove・ウォッシュ光・カメラ/ライト補助)は [scripts/blender/studio.py](scripts/blender/studio.py) の共有モジュールに正本化されており、全シーンスクリプトが同じ「部屋」で撮る。

**2つ目の実証: tote-canvas(2026-07-15)**: 布のドレープを3Dディスプレイスメントで作り、**PrintSurface シェルに同じ変位フィールドを共有させることで、焼いたUVマップがロゴをシワの中まで曲げる**。あわせて PrintLight でキャンバス織り目がロゴに乗る。「素材感・曲面・ドレープの上への印刷」という Blender ならではの領域の型がこれで揃った。

**焼き出される3パス**: `stage.png`(PrintSurface非表示のビューティ)/ `uvmap.png`(16-bit PNG。R=u・G=v・B=カバレッジのプリマルチプライドUVフィールド)/ `light.png`(PrintSurfaceを白ディフューズにした陰影マップ。ロゴに乗算される)。エンジン側は `surface.uvWarp` があるとホモグラフィの代わりにUVフィールド経由でロゴを逆写像する([engine/uvwarp.ts](engine/uvwarp.ts))。曲面(円筒等)の回り込み・遠近圧縮・実シーンの陰影が決定論のまま得られる。

**実測制作コスト**(M系CPU・1600×1200・128サンプル): レンダー約3分/テンプレート+シーン調整の試行。オーダー時の合成は約0.6秒・変動費ゼロ(jobs.jsonl 実測)。

**スタジオ背景のレシピ**(2026-07-15 確立・今後の全3Dテンプレート共通): 無限背景は **大半径 cove**(1枚のフィレット面。`build_cove` の radius≈1.3m=実スタジオ相当)+ **大きなソフト面光の均一ウォッシュ** + **低露出**(背景アルベド0.60)。小半径・強照明にすると①床が255に白飛び ②cove の曲面部に暗い谷=壁線、が出て「階段状」になる。**滑らかさの判定は目視ではなく数値で行う**——背景の縦1列の輝度が「単調増加・clip(255)ゼロ・局所反転(谷)ゼロ」かを測定して合否を出す(微妙な階調段差は目視で誤判定しやすいため)。明るさ・マグの陰影の最終調整ツマミ: `studio_matte` アルベド / `BGWash` energy / world strength(明るさ)、`Key`・`Rim`(マグの立体感)、cove `radius`(滑らかさ)。

### 焼き込み(Blender)= 固定 / 合成(TS)= 可変 の仕分け

同じテンプレートで「何が1回焼けば固定され、何が注文ごとに自由か」を明確にしておく。`stage.png` は「その明るさ・アングル・比率で撮った1枚」なので、そこに焼き込まれた属性を変えるには **Blender 焼き直し(約3分)** が要る。ロゴは焼き込まれず毎回載せるので軽い。

| 変えたいもの | どちら | コスト |
|---|---|---|
| ロゴの差し替え | 合成(TS) | 約0.6秒・変動費ゼロ |
| ロゴの位置・大きさ・色・不透明度 | 合成(TS) | 同上(焼いた印刷面の中で自由) |
| 出力**解像度**(比率そのままの拡大縮小) | 合成(TS) | `width` 指定のみ |
| 背景・マグの**明るさ**、ライティング、アングル | **焼き込み(Blender)** | 焼き直し |
| **縦横比**(4:3 / 16:9 / 正方形 等) | **焼き込み(Blender)** | 焼き直し |

比率・明るさのバリエーションは **それぞれ別テンプレートとして1回ずつ焼く**のが正しい持ち方(同じ `.blend` からカメラ解像度・ライティングだけ変えて量産できる。焼いた後はどの版でもロゴ差し替えは同じく約0.6秒)。プレゼン本編のレイアウト(1カラム4:3・正方形2枚並列 等)が固まったら、必要な比率の版を運営が焼いておく。

1. `labs/workflow/templates/<id>/` を作り、`template.json`(仕様は [core/template-format.ts](core/template-format.ts))と舞台アセット(SVG推奨=解像度非依存)を置く

### ロゴのプライバシー(Phase 1)

ロゴは合成時に**自サーバー(Next.jsのRoute Handler)にのみ**送信される。外部AI・外部APIには一切送らない(Phase 3の舞台生成でも、送るのはプロンプトのみでロゴは送らない設計)。
