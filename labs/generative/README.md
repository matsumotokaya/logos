# Generative Lab — 探索モード(生成AIハーネス)

生成AIにロゴを解釈させ、決定論では作れない表現を探す研究所。実験場は `/labs/generative`(Phase E1 稼働中)。

この文書は**探索モード開発要件の正本**(事業側の要件書 2026-07 を反映)と**実装状況**、この構想に至った**経緯**を兼ねる。[Workflow Lab の基盤要件書](../workflow/README.md)の続編であり、技術選定はディープリサーチ(2026年7月実施)に基づき決定済み。基盤要件書と本書で矛盾を見つけた場合は、実装ではなく質問で解消すること。

## 経緯 — なぜ「保証」と「探索」の二層になったのか

このプラットフォームのラボ群は、当初「Motion / Image / Video / Workflow」という技術ジャンル別の4ラボ構想だった。しかし基盤要件書(決定論的合成)の実装を進める中で、本当の分類軸は技術ジャンルではなく**「ロゴに触れるか、触れないか」**だと分かった。

- **保証モード**: ロゴを1ピクセルも崩さないことが**保証される**領域。SVG/3Dによるプレゼンテーション表現(Motion Lab)と、テンプレート合成+Photoshop・Figma・Blender連携のワークフロー(Workflow Lab)の2ジャンルからなる。ガイドライン・定番モックアップ・印刷入稿物など「絶対に崩せない用途」を担う、**プロダクトの根幹**。通常業務で使うのはこちらで、内部は複雑なワークフローの積み重ねになる。
- **探索モード**(本書): その信頼の上で**可能性を解放する**領域。生成モデルがロゴを解釈・変形することを仕様として許容し、雪山の看板に風化して馴染むロゴ、ネオンサイン、刺繍——決定論では絶対に作れない表現を扱う。見た目・情緒のインパクトを最大化できる代わりに、プロの現場で使えるかどうかは**使う人がリスクとリターンを判断する**。生成コスト(実費)もかかる。構成要素はハーネスプロンプト×生成AI APIの組み合わせで、保証モードに比べれば構造はシンプル。

つまり二層構造とは: 保証モードが「このプラットフォームはロゴの扱い方を心得ている」という**信頼の証明**であり、探索モードは「その信頼の上で可能性を解放する」レイヤー。探索モードが確率論的であることを**隠さずに提示する**——「保証」と「探索」がUI上も明示的に分かれ、探索側にはQAゲートがスコアを付けて返す——ことが、プロダクトとして誠実な設計になる。

### 画像と動画を同じラボにする理由

動画生成は、ほぼ間違いなく**参照画像**を起点にする(image-to-video)。「生成したブランドイメージを、次に動かす」という一連の流れになるため、画像生成と動画生成を別ラボに分けると流れが分断される。よって旧 Video Lab 構想のうちショートビデオ生成はこのラボに統合した。

なお、各シーンの単発アセットを組み合わせて**プロモーションビデオ・CM・バナー・LP**という最終的なマーケティング成果物に仕立てる「統合」の領域は、さらにその先にある別の実験場([Campaign Lab](../directory.ts)、現在はプレースホルダー)として区別する。マーケの最終出力は常に組み合わせで生まれるからである。

## 設計思想(全実装判断の基準)

**ハーネスとは、逸脱を禁止することではなく、逸脱を種類別に制御し、計測し、ユーザーに見せることである。**

保証モードの原則が「ロゴに触れさせない」だったのに対し、探索モードでは生成モデルがロゴを解釈・変形することを**仕様として許容する**。ユーザーはリスク(ロゴが変形しうる)とリターン(決定論では作れない表現)を理解した上で使う。プロダクトの責務は次の2点:

1. 逸脱の**方向**をダイヤルで制御可能にすること
2. 結果の**逸脱度**を計器盤としてユーザーに提示すること

この原則から導かれる推論: **「崩れたから失敗」ではない。「意図しない方向に崩れ、かつそれをユーザーが把握できない」が失敗である。**

QAゲート(基盤要件書 Layer 4)の「ロゴ忠実度スコア」は、保証モードでは内部回帰テストだが、探索モードでは**ユーザーに提示する品質指標**に転用する。「この生成物のロゴ忠実度: 94%」という見せ方は、ハーネスエンジニアリングという概念そのものをUIで可視化することであり、他のどの生成ツールもやっていない差別化になる。

## アーキテクチャ

基盤要件書の Layer 3(舞台生成層・プロバイダ抽象化)と Layer 4(QAゲート層)を拡張する形で実装する。横断要件(データ取り扱い・コスト計測・監査ログ)は基盤要件書のものがそのまま適用される。

### E-1: 生成エンジン層(3エンジン構成)

プロバイダ抽象化レイヤーの上に、役割の異なる3エンジンを統合する:

| 役割 | エンジン | 担当 |
|---|---|---|
| **主エンジン(世界構築)** | Together経由の **FLUX.2** | マテリアル変換、環境統合、シネマティックな「世界内存在」表現。マルチリファレンス編集(最大10参照画像)と4MP出力を活用 |
| **派生生成機(造形展開)** | **Recraft** | ロゴの造形言語からのパターン、背景システム、アイコン群、ベクター系展開。`image_to_image` の similarity strength をダイヤルとして活用。SVG出力対応 |
| **対話修正層(アートディレクター)** | Vertex AI経由の **Gemini 3 Pro Image** | マルチターン編集(ラフ→修正→ムード微調整)。最大14画像入力 |

契約面の許可/禁止リストは基盤要件書に準拠。**Ideogram、OpenAI GPT Image 2 は本番パイプラインで使用しない**が、E-6のベンチマーク運用でのみ扱う。

### E-2: 表現テンプレートシステム

探索モードの生成は自由プロンプトではなく、**表現テンプレート**を起点とする。

- タクソノミーは6系統: ①マテリアル変換 ②環境統合 ③様式化・アートディレクション ④展開・派生 ⑤タイポグラフィ演出 ⑥シネマティック・キーアート。テンプレートは必ずいずれかの系統に属する
- **テンプレートの命名・設計単位は「アートディレクション」とする**。「ネオン看板」ではなく「1980s Tokyo alley sign」、「かっこいい写真」ではなく「premium outdoor fashion campaign」のように、世界観・時代・撮影様式まで含んだ単位で定義する
- テンプレートのデータ構造(**コード変更なしで追加可能**にする。Motion Lab の実験プラグイン・Workflow Lab のテンプレートディレクトリと同じ思想):
  - **プロンプト骨格**: 「ロゴを何として存在させるか」を先頭に(例: powder-coated metal channel letters)、続いて環境・光・カメラ・材質・ムードの順。ユーザー入力(業種・キーワード等)はこの骨格にラップしてからモデルへ渡す。**生のユーザープロンプトを直接モデルに渡さない**
  - 使用エンジンと推奨パラメータ(参照強度・similarity strength 等)の初期値
  - ダイヤル4軸(E-3)のデフォルトとロック指定(「このテンプレートでは文字保持を無効」等)
  - 対応ロゴ種別(シンボル型/ワードマーク型)の宣言
- **初期リリースは「成功しやすい演出類型」に絞る**。調査結論に従い、商用品質に近い①マテリアル変換と③様式化から先行し、⑥シネマティックはばらつきが大きいため厳選した少数のみ。**テンプレート数より1テンプレートの成功率を優先する**

### E-3: ダイヤルシステム(逸脱の制御)

- UIの主操作は単一の「忠実度スライダー」では**なく**、内部的に**4軸(形状保持・色保持・文字保持・世界観自由度)**で構成する。ただしユーザーへの初期提示は**プリセット3段(厳密/バランス/自由)**とし、詳細展開で4軸を個別調整できる**2階層UI**とする
- 4軸から各エンジンのパラメータへのマッピング層を実装する:
  - **形状保持**: ControlNet系の edge / line-art 条件付け(シルエット固定・素材自由の中間点)、参照強度
  - **色保持**: 参照画像の色条件、プロンプト内カラーパレット指定(ロゴから自動抽出済みのパレットを使用)
  - **文字保持**: ワードマーク領域の扱い(E-5)
  - **世界観自由度**: プロンプト骨格の環境記述の強度、参照強度の逆数側
- マッピングの実装値はテンプレートごとにチューニング可能とし、**ハードコードしない**

### E-4: 逸脱スコアボード(基盤要件書 Layer 4 の拡張)

QAゲート層を拡張し、探索モードでは**判定結果をユーザー向けの計器盤として表示**する。保証モード(内部回帰テスト)と探索モード(ユーザー向け表示)は**同一のスコアリング基盤を共有する**。

4段構成のスコアを実装する:

1. **シルエット類似**: ロゴと生成物内ロゴ領域を二値化し、輪郭・主要辺・穴構造を比較(形状ベース。商標検索系の shape similarity の考え方を参考にする)
2. **知覚類似**: LPIPS系による見た目の近さ
3. **文字保持**: ワードマークの場合、OCRによる文字列一致率
4. **意味類似**: CLIP系 embedding による抽象的な近さ

表示は**総合値+4軸分解**(例: 総合82/形状91・色76・文字58・雰囲気94)。単一値のみの表示は不可——**「なぜ82なのか」が説明できることが計器盤の要件**。生成物内のロゴ領域の特定(検出)が前提となるので、ロゴ検出処理を含めて設計すること。

スコアは全生成物に対して記録し、テンプレート別・エンジン別の成功率分析に使えるようデータ設計する(**この蓄積が製品の資産になる**)。

### E-5: ワードマーク対策

小さな文字を含むロゴの複雑シーン統合は現行モデルの弱点であり、これは**UXで扱う**:

- ロゴ前処理(基盤要件書のSVG前処理を拡張)でワードマーク/シンボル/複合を分類する
- ワードマーク型に対しては、文字をそのまま読ませる表現ではなく、**モノグラム・頭文字・大きな短語・分割表示への再構成を提案するUXフロー**を用意する(複合型ロゴならシンボル部分のみの抽出を提案)
- テンプレート側の対応宣言と組み合わせ、成功率の低い組み合わせは**生成前に**警告または代替提案を出す

### E-6: ベンチマーク運用(社内向け)

- Ideogram 4.0 と GPT Image 2 は表現上限の比較対象として、**社内評価ハーネス**に常設する(契約再考の判断材料の継続収集)
- **重要: ベンチマークに顧客ロゴを絶対に使用しない**。社内テストロゴセット(自社制作のダミーロゴ)のみを使用する。契約除外モデルへの顧客データ送信はいかなる目的でも禁止
- 定期実行(月次目安)で、代表テンプレート×テストロゴの生成結果とスコアを本番エンジンと並べて記録する仕組みを作る

### E-7: マルチターン改善UX

探索モードは一発生成ではなく**対話で寄せる**前提で設計する:

- **生成セッション**の概念を導入: 初回生成→方向修正(Gemini対話層)→ダイヤル調整→再生成、の履歴を保持
- セッション単位のコスト計測(基盤要件書の横断要件を拡張。マルチターンはコストが嵩むため、**セッション上限とユーザーへの残量表示**を設計に含める)
- 気に入った生成物はブランド資産(貯める場)へ保存。**スコアと生成パラメータも一緒に保存**し、再現・派生ができるようにする

### 動画(ショートビデオ)——旧 Video Lab から統合

- ショートビデオAPI(Seedance / Veo / Kling / Higgsfield / Runway)の品質・コスト・レート制限・商用条件の実測。**1本あたり実費の把握が課金設計の数字の根拠になる**
- 方式は image-to-video を基本とする: このラボの画像生成(またはWorkflow Labの合成出力)を参照画像として動かす
- 無料キャンペーン(例: 3回無料)の原価計算——体験原資の単価が集客設計に直結する
- ※30秒プロモの「組み立て」(テンプレート駆動のコンポジション+テロップ+BGM)は動画生成ではなく統合の領域なので Campaign Lab(将来枠)へ

### 画面構造(2026-07-14 再設計: ロゴが主語)

ページの主語は**選択中のロゴ**。ロゴを切り替えると、その下の全てが連動する:

1. **LogoRail** — ロゴ選択(全ラボ共有レジストリ)
2. **LogoReport**([components/LogoReport.tsx](components/LogoReport.tsx)) — **そのロゴの生成レポート**。ダイヤル検証シートと同型: 生成済みテンプレートごとにプリセット3列(厳密/バランス/自由)を並べ、各結果に計器盤(4軸ダイヤルバー+エンジン/実費/秒数/実寸)を付す。未生成プリセットはプレースホルダから直接生成に誘導。同プリセットの過去生成は履歴行へ
3. **表現テンプレート** — このロゴで次に試すアートディレクション。カードのプレビューは**このロゴの最新生成のみ**(他のロゴの生成物は絶対に混ぜない)
4. **原価計測パネル** — ラボ全体の集計

ロゴとレコードの紐付けは `logoHash`(送信ペイロードのSHA-256先頭16桁)。ブラウザ側も同一アルゴリズムでハッシュを計算し(`core/client.ts` の `computeLogoHash`)、`jobs?logo=` でそのロゴのレコードだけを取得する。E2の忠実度スコアはこのレポートの計器盤(現在「E2で計測」と予告表示)に載る。

### 実機検証の結果(2026-07-13 実施・完了)

両エンジンとも実キーでの生成に成功。判明した仕様(詳細コメントは各プロバイダ実装内):

1. **Together / FLUX.2 [pro]**([engine/providers/together.ts](engine/providers/together.ts)):
   - `reference_images` の **data URI は受理される**(一時URL化は不要)
   - `guidance_scale` / `negative_prompt` / `steps` は **400で拒否**(proはマネージド設定)。数値制御が要るなら [flex] を検討。ダイヤルの数値側はプロンプト指示文で機能する(下記シートで確認)
   - 総ピクセル **3.69MP〜10.4MP 必須**(1024²不可)→ プロバイダがアスペクト比を保って自動スケール
   - 正常時 26〜49s/$0.03。一時的な5分超のキュー詰まりを1回観測(Node fetchの300s上限で失敗、コスト0で記録済み)
2. **Recraft**([engine/providers/recraft.ts](engine/providers/recraft.ts)):
   - モデルslug `recraftv4_1` は**有効**。ただし **V4.1はイラスト系style(digital_illustration等)を400で拒否** → イラスト系styleは `recraftv3` を自動選択(`engineParams.model` で明示上書き可)
   - `response_format: b64_json` 対応(即時回収OK)・`negative_prompt` 対応。8.2s/$0.035
   - 将来フック: `controls.colors`(パレット条件付け=色保持ダイヤルの強化候補)、`controls.no_text`(E-5の文字抑制候補)
3. **未解決事項1(ダイヤル実効性)**: weathered-alpine-signage×プリセット3段の実生成比較で**知覚可能な差を確認**(一次クリア)。実ロゴ(XTRUSTワードマーク)での再検証も完了し、検証シート(Artifactと `var/generative-lab/dial-verification-sheet-01.html`)を事業側レビュー用に作成済み。定量化はPhase E2のスコアボードで
4. **ワードマークでの追加確認(2026-07-14)**:
   - **参照画像の最小サイズ**: Together=高さ256px以上 / Recraft=最小辺256px以上。横長ワードマークが弾かれたため、ラスタライザが短辺256未満を白パディングで補正済み([engine/logo-raster.ts](engine/logo-raster.ts))

### テンプレートの追加手順(コード変更不要)

1. `labs/generative/templates/<id>/template.json` を置く(仕様は [core/expression-format.ts](core/expression-format.ts)。命名は「アートディレクション」単位、`prompt.existence` が先頭)
2. 実験場をリロードする。バリデーションに通ればカタログに出現し、エラーがあればカードにエラー内容が表示される

### データ取り扱い(実装済みの担保)

- ロゴが外部に送られるのは**選択テンプレートのエンジン1社のみ**(Together=ZDR既定 / Recraft=学習不使用規定)。モック時はサーバー外に出ない
- 生成物は受領後ただちに **Cloudflare R2**(`labs/generative/outputs/<name>`)へ回収し、R2未設定の開発環境のみ `var/generative-lab/outputs/` へフォールバックする。以後は自前URL(`/api/labs/generative/outputs/[name]`)のみを参照する(Recraftの約24h公開URL対策)
- 全ジョブを `var/generative-lab/jobs.jsonl` に記録: 監査(`logoSentTo`+ロゴhash)、原価(`costUsd`、失敗時も実費を計上)、成功率分析(テンプレート・エンジン・プリセット・ダイヤル・**実行プロンプト全文**)。この蓄積がE2スコアボードの土台になる

## 未解決事項(実装前・実装中に検証し、事業側とreviewする)

1. **ダイヤル4軸の実効性**: 4軸→パラメータのマッピングが実際に知覚可能な差を生むか。Phase E1で代表テンプレート1つを使い、軸ごとの変化を並べた検証シートを作成する
2. **スコアの安定性**: LPIPS系は敵対的な不安定性が指摘されている。マテリアル変換(刺繍・ネオン等)の正解サンプルでスコアが直感に合うかを検証し、必要なら4軸の重み・手法を調整する
3. **ロゴ領域検出の精度**: 生成物のどこにロゴがあるかの検出が全スコアの前提。環境統合系での検出失敗率を計測する
4. **スコアの表示閾値・色分け**(何点から「警告」か)はUX判断なので、データが溜まった段階で事業側と決める。ハードコードしない
